## 问题 1：流程状态与产品代码同树，指纹靠排除清单区分

**现状**：流程记录散在 `docs/specs/**`、`docs/metrics.md`、`docs/task-pool/**`，另有 Agent 知识 `MEMORY.md`、`.knowledge/**`。状态指纹 `template/scripts/ai-state-id.sh` 对全仓取哈希再逐项排除：两处 `case`（`:103` 未归属检查、`:134` 未跟踪文件）与两条 pathspec（`:131-132`），`ai-verify.sh:45` 另有一处目标检查。`MEMORY.md` 与 `.knowledge/` 至今不在排除清单内——写一条经验就会让验证摘要过期（feat-t-000014 实际遇到，只能推迟到归档后写入）。脚本中引用这些路径的文件分别有 10、3、7、1、3 个。每新增一种流程文件就要补清单，代码或构建引用流程目录时会漏验。

| 方案 | 做法 | 代价 |
| :-- | :-- | :-- |
| 1A 隐藏单一根 | 全部流程记录与 Agent 知识迁入 `.harness/`，指纹只排除这一个根 | ripgrep 默认跳过隐藏目录，Claude Code 的 Grep / Glob 与部分 IDE 搜索会「看不见」Spec 与任务池；与现有 `harness/`（验证配置，须计入指纹）、`.ai-harness/`（安装清单）三名并存，易混淆 |
| 1B 可见单一根 | 同 1A，但根为非隐藏的顶层目录 `process/` | 一次性迁移：脚本路径、指南、README、下游 upgrade；下游可能已有自己的 `process/`，upgrade 须先检测并拒绝（与 retrofit 保护已有文件一致）；文档站若扫描整个仓库仍可能收录（扫 `docs/` 的常见配置不会） |
| 1C 白名单指纹 | `verify.conf` 声明验证依赖的路径，指纹只算这些；未声明回退现有算法 | 不迁移；漏声明即漏验，脚手架无法替项目判断，责任转给配置 |
| 1D 维持排除清单 | 补上 `MEMORY.md`、`.knowledge/`，靠指南约束 | 无迁移；每新增流程文件补一次，漏验靠约定 |

**推荐 1B**。迁移语义：
- **迁移方式**：upgrade 用 `git mv` 一次性搬迁，要求工作区干净；不做新旧路径双读兼容期，脚本只认新路径，旧路径存在时报错并提示运行 upgrade。
- **在途 Spec**：迁移只在没有进行中 Spec 时执行（upgrade 检测到活跃 Spec 即拒绝），不处理在途 Spec 的指纹、审查状态与 §4 清单中的流程路径；`.gates` 随归档 Spec 目录一起移动，G3 委托快照只哈希 design.md 中的委托文本（`ai-gate.sh:75-78`），与路径无关。
- **历史**：归档 Spec 中的旧路径引用保持原样不改写；`git log --follow` 可追溯单个文件。

## 问题 2：门禁用正则判断自然语言

**现状**：G2 扫描 AC 行的含糊词（`ck_g2`，`ai-gate.sh:195-237`）。G6 已要求逐条 AC 以 `- AC-xx：通过` 开头（`:572`），但同一行剩余文本、「冒烟或 E2E 证据」行和「对照 AC 的检查结果」行（`:557-565`）仍做关键词扫描，并对后两行用 `G6_PASS_RE` 做正向判定；零计数与引号豁免使这部分达到约 130 行（`:465-596`）、53 例样本跑在三种 awk 下。每次放宽或收紧都引出新边角（T-000022~T-000024）。T-000013 时维护者否决过「改为行首结构化判定」而选了豁免路线；本 ADR 重提，因为豁免路线已证实没有终点。

| 方案 | 做法 | 代价 |
| :-- | :-- | :-- |
| 2A 只认结构化结论 | G6 三处都只读结构化结论：逐条 AC、AC 汇总与冒烟各写 `通过` 或 `不通过`，后接证据文本不扫描；G2 只查 AC 表格完整，不再扫描词表，含糊与否交给 G5 审查清单 | 删除 G2 词表与 G6 扫描代码及对应用例，不保留旧检查：已归档 Spec 不再跑门禁；upgrade 要求没有停在 G6 之前的在途 Spec，或其 acceptance.md 按新格式重写后再过 G6，因此无需按版本区分新旧格式；放弃「证据里出现失败就拦」的自动发现，矛盾记录由 G5 / 人发现 |
| 2B 降为提示 | 词表与关键词扫描保留，只警告不阻塞；G5 清单核对警告 | 改动最小；扫描代码与边角用例仍在，验证成本不降，边角仍会被报告 |
| 2C 冻结现状 | 保留硬拦截，不再处理边角 | 无改动；误拦持续（如「通过 12 失败 0」） |
| 2D AC 绑定机器检查 | 每条可自动化的 AC 绑定一条检查命令或测试 ID，`ai-verify.sh` 记录各自退出码，G6 只读机器结果；人工观察类 AC 仍需人确认 | 最彻底地去掉文本判定；需要扩展 AC 表格式、验证摘要与 G6，工作量最大；文档类、体验类 AC 无法绑定命令 |

**推荐 2A**，2D 记为后续方向（2A 落地后若仍需自动发现矛盾再评估）。2A 不再引入任何新的文本规则，符合「改结构」的要求。

## 问题 3：正式验证是全量单体，且与审查强绑定

**现状**：`harness/verify.conf` 的 `CUSTOM_CHECK` 跑 `tests/verify-repo.sh`：diff 空白校验 → 完整模板自检（13 节）→ CLI 回归。G4 比对全仓指纹，G5 要求审查状态等于验证 state（`ai-gate.sh:452-457`），审后任何改动 = 全量重验 + 新一轮审查。本仓库未配置 CI。

| 方案 | 做法 | 代价 |
| :-- | :-- | :-- |
| 3A 自检分片 | 按节拆成独立文件与共享夹具；快检按改动路径只跑相关分片，正式验证仍跑全部 | 一次性重构自检；正式验证时长不因分片下降 |
| 3B 降低单片成本 | 第 2、3 节共享已生成的夹具，减少每例新开 bash 与 awk 进程 | 局部优化，收益随用例增长回涨；成本低，可最先做 |
| 3C 审后增量复核 | 审后只改测试或注释时，在原轮次内附加增量复核 | 削弱「审后不可偷改」；风险最高 |
| 3D 本地分片、全量交 CI | 正式验证只跑受影响分片，全量回归由 CI 承担 | G4 证据来源改为 CI；本仓库无 CI，需先建；跨宿主接手时要能读到 CI 结果 |

**推荐 3B 先行，再做 3A；不做 3C；3D 待有 CI 后再评估**。问题 2 采用 2A 时会删掉相当一部分第 2、3 节用例，进一步缩短时长。

## 问题 4：任务池没有分诊

**现状**：`ai-task-pool.sh` 只认队列状态「待办 / 暂缓 / 取消」（`:75`），`next` 按 ID 选未关联的待办（`:89`），优先级字段仅作信息；没有改状态的子命令。每条收录都是一个要走 G1~G7 的 Spec 候选，一行级问题与降低全局成本的任务同等排队。T-000025 原件要求区分顺手修、引入真实优先级、同模块合并，维护者已说「那就按照建议顺序A加D一起做」。

| 方案 | 做法 | 代价 |
| :-- | :-- | :-- |
| 4A 两类条目 | 收录时分「Spec 任务」与「顺手修」；顺手修记目标文件，`ai-resume.sh owner` 在 Spec 的 §4 清单触及该文件时列出，该 Spec 顺带处理并在归档时勾销 | 改任务池脚本、resume 与指南；需定期清理长期无人触及的顺手修 |
| 4B 有效优先级 | 优先级参与排序（P0 > P1 > P2，同级按 ID），`prefer` 保留 | 改「默认按收录顺序」的既有设计；收录时多一步判断 |
| 4C 合并规则 | 指南写明同模块建议归档时合并为一条 | 无代码；单独使用时依赖自觉 |
| 4D 状态子命令 | 增加改队列状态的子命令（如 `defer` / `cancel`，附理由写进补充记录） | 小改动；没有它，分诊只能手改字段 |

**推荐 4A + 4B + 4C + 4D**，即 T-000025 原件的完整范围加状态子命令。草稿曾建议 4B 暂不做，与维护者已作的「A加D」决定冲突，已改回。
