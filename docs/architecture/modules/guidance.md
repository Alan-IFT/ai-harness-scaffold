# 项目指南

- **范围**：`template/AGENTS.md`（规则入口）、`template/.agents/skills/`（按阶段读的指南）、Spec 模板与 `README.md`。
- **为什么只写一份入口**：各 AI 工具都能读 `AGENTS.md`，`CLAUDE.md` 只做导入；规则写两份就会分叉。
- **为什么保留只有一行导入的 `CLAUDE.md`**：Claude Code 新版能直接读 `AGENTS.md`，但默认只在工作目录及上级都没有 `CLAUDE.md`、`CLAUDE.local.md` 时才读，有些会话还读不到。删掉它只省一行，用户一加 `CLAUDE.local.md` 放个人说明，规则就整份不再加载；留着这行导入，各种情况都读得到，也不会读两遍。依据是官方文档 `code.claude.com/docs/en/memory`（2026-11-10 复核），再提议删除前先看它当时的说法。
- **为什么指南只引用配置键**：阈值以项目自己的 `harness/redlines.conf` 为准，指南里写死数字会和配置不一致。
- **为什么方案并进 tasks.md、人的决定并进 review.md**：`design.md` 与 `acceptance.md` 只被格式检查读过，真实缺陷都由独立审查发现（ADR-0003）。
- **为什么「需人决定：是」要先审方案**：编码后再推翻方案代价最高；任何宿主都能用新会话或 subagent 做这一步。
- **为什么审查者要复核「需人决定」、对照记忆与模块活文档、只拦本次引入或加重的问题**：「需人决定」是 g3 要人当次决定的唯一开关，却由写方案的 AI 在 g1 自判、不进状态指纹；项目记下的坑不在审查者眼前，改动让文档说谎就没人发现；老问题挡门会逼实现者改需求外的代码。审查后才改为「是」的不补审方案：g3 现读该字段、要人当次决定，代码已写完再审方案只是走形式。取自 Claude Code 团队的审查实践（2026-10-30 评估）。
- **为什么「待确认问题」按后果划线，不按 AI 觉得有没有歧义**：AI 自己拍板偏偏发生在它觉得有常规默认的时候，宿主工具的常驻指令也这样要求它（有常规默认的自己选、说一声、继续）；歧义显眼的需求它本来就会先问。2026-11-21 的沙箱对照（`process/specs/archive/2026-11/feat-t-000055/tasks.md`）：同一句「加个参数，可以只导出某个客户的订单」，旧文字下 Sonnet 5.5 和 Haiku 5.5 共 6 次里 4 次自己定（3 次自己写结论、自己勾选并过完三道门，1 次没走流程直接改完），同一个没定的点定成了三样；加这条规则后那 4 格各跑 1 次，都停在 g1 先问，清楚的需求没有多问。后来同一句清楚的需求先后跑了 13 次，有 5 次停在 g1 问了输出格式、参数先后这类细节（`process/specs/archive/2026-11/feat-t-000057/tasks.md`）。Fable 5.2 在同一格旧文字下本来就先问了最要紧的一点，加规则后交人定的点从 1 个变成 3 个。维护者同日选定：按后果划线，规则加审查复核，人不在时停在 g1，不改脚本。已知的口子：g1 只查有没有未勾选项，查不出是谁答的，不照做的靠审查指南里那半句拦（对照里 Sonnet 5.5 审查，旧文字 3 次都没拦，新文字 3 次拦住 2 次；Fable 5.2 审查，新旧文字各 1 次都拦了；后来同一份样本上 Sonnet 5.5 审查者带着那半句共审了 8 次，只有 2 次拦了）；问题清单不保证列全，没列出来的点仍是 AI 自己定；人不在时一个要问的点会堵住整个队列。README 只写使用者会被问、可以怎么回，不抄判据。
- **为什么没有把「个人偏好里的事先授权」写进 README**：嫌 AI 问得多时，本可以不收紧规则，让人在个人偏好里写一句带范围的授权，范围内的问题按推荐定、做完列出来。2026-11-22 在沙箱里试了一句（「命令行细节和输出格式直接按你的推荐做，做完列给我；涉及数据、文件路径、和活文档冲突的仍然先问我」，写在项目的 `PREFERENCES.md`），带这句话跑了 11 次流程，另用一句宽泛的跑了 2 次（`process/specs/archive/2026-11/feat-t-000058/tasks.md`）。按跑之前写定的规则没有通过，README 就没提它：「按客户导出」的 5 次里，要求每次都把「写到哪」落盘留给人，做到的是 3 次；要求「参数怎么写」按这句话定下并写明依据的至少 4 次，实际是 3 次。「写到哪」没做到的 2 次，一次是 Sonnet 5.5 整份 Spec 没提它，只因为把「怎么匹配」当成数据留给了人才停在 g1；一次是 Haiku 5.5 四个点都问了，但没收录、只写在回复里。规则之外看到的：Sonnet 5.5 和 Fable 5.2 的 9 次，回复里都说按这句话定了范围内的点并逐条列了出来，「按客户导出」留给人的问题从 3~4 个变成 1 个（4 次都是），清楚的需求 5 次都没停（此前没有这句话时 Sonnet 5.5 13 次里 5 次停，不是同一批，Fable 5.2 没有参照数，所以只能说没有多停）；定下的点 5 次在 Spec 里写了依据，1 次含糊，3 次只写在回复里，事后分不出哪些是按授权定的、哪些是 AI 自己定的；Haiku 5.5 的另一次没收录就直接改了代码，理由里引了这句话。宽泛的那句（「少问我，小事你自己定，做完告诉我」）2 次都没被当成授权，四个点照旧全问。没测的：审查拦不拦按偏好定下的点（走完流程的 5 次，自己起的 Sonnet 5.5 审查都没异议）、通用偏好文件、别的写法、Codex 等工具；偏好文件不入库、没有历史，那句话是不是人写的也核不了。偏好里的事先授权算不算人的答复，没有定：规则写的是「人明说「你定」「按推荐」」，README 写的是回了才算，沙箱里 Sonnet 5.5 和 Fable 5.2 把它当成了答复。同一天维护者定下，上一条说的两个口子先不堵：真实项目里出现一次「没问、做错、返工」，就改成每个需求先确认复述再开工（当初没选的 Q1-B）；出现一次自答自勾过了 g1，就让 g1 校验勾掉的问题带日期和答复原话（当初没选的 Q2-C），上之前先在沙箱里看它会不会把 AI 逼得不列问题。
- **为什么写明正式验证前先提交代码**：状态指纹把没暂存和已暂存算成两种状态，验证通过后才 `git add`、提交，指纹就变了，验证过期，要重跑一遍，审查记下的状态也跟着对不上；feat-t-000055 的沙箱里走到正式验证的 7 次流程有 4 次因此重跑。写在「验证」一条里并带上原因，是因为同一节上面写着任务「完成后先验证再勾选并提交」，那说的是任务自己的验证。两次对照都是 Sonnet 5.5、每边 3 次：feat-t-000056 数「验证过期的提示」，两边都是 0，比不出来；feat-t-000057 改看「第一次正式验证前代码提交了没有」，旧文字 3 次里 1 次、新文字 3 次里 2 次，这一次旧文字有 1 次流程验证过期后重跑，新文字没有。只差 1 次，证据偏薄，新文字下也有 1 次没照做。彻底的办法是指纹只按文件内容算（`T-000051`，暂缓）。
- **为什么编码原则用 Karpathy 准则原文**：维护者 2026-10-25 定下吸收原文，重复处以它为准，与流程、红线有歧义时交人决定；同一说法只留一处，指南不复述 AGENTS.md。
- **为什么个人偏好单独放 `PREFERENCES.md` 且不入库**：语言、语气这类习惯因人而异，写进 `MEMORY.md` 会变成全队的“项目事实”；不入库也就不进状态指纹，改偏好不会让验证过期。
- **为什么通用偏好放 `~/.ai-harness/PREFERENCES.md`**：宿主自带的偏好注入只对那个宿主生效，换工具就丢；写进 `AGENTS.md` 的读取规则对所有工具都有效，一份文件跨项目共用。目标项目不知道脚手架仓库在哪，所以放用户目录而不是脚手架仓库里。
- **为什么写明 AI 工具自带的记忆不作来源**：工具会把经验记进自己的记忆目录，换一个工具接手就读不到；2026-11-09 核对本仓库时，就有几条经验只存在 Claude Code 的记忆里。不宜入库的项目事实没有别的位置，所以放进不入库、每次接手又都会读的 `PREFERENCES.md`，不另开文件。
- **为什么小改动的出口只列源码注释和说明文档**：本仓库的 `AGENTS.md` 早有「非平凡变更走三道门」，模板里却没有对应的话，界线全凭各工具自己判断。只放行列得出的：规则、指南、配置、Spec 模板和脚本里的字符串，措辞就是行为，列「除外」清单总会漏。有活跃 Spec 时不放行，因为状态指纹按全仓算，一次小改动就会让它的验证过期。
- **为什么 README 讲结构不抄规则**：只有安装说明时，读者判断不了项目是什么、怎么运转（维护者 2026-11-06）。README 写问题、流程、架构和脚本与配置的总览；门的完整规则和操作步骤留在 `template/AGENTS.md` 与指南，避免两边分叉。英文版只做摘要，因为产出的规范都是中文。
- **改动时**：同步检查 `skill/SKILL.md` 与自检，确保指南里的命令与脚本一致。
