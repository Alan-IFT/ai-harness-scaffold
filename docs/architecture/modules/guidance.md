# 项目指南与文档

- **新需求入口**：维护者直接向 AI 提需求；AI 区分独立新需求和已有需求的补充，分别用 `intake` 自动收录与路由、`update` 追加。活跃 Spec 先续做；否则人工 `prefer` 指定的一次性下一项优先，默认按 T-ID 收录顺序。`start-next` 原子选取并建 Spec。旧 `docs/INTAKE.md` 保留历史，不和任务文件重复记录原文。

- **职责**：`template/AGENTS.md` 给目标项目提供跨 IDE 入口；`template/.agents/skills/` 是按阶段读取的普通 Markdown；`skill/SKILL.md` 是仓库内共享技能入口，Codex/Claude Code 用户技能目录只放带源路径的薄适配器。主 Agent、限定任务 worker 和 G5 审查者按角色读取项目原件，避免转贴整个 Spec 或上一 Agent 对话。
- **边界**：项目事实写在任务文件、Spec、活文档与 Git 中；任务文件只关联稳定 Spec ID，创建脚本拒绝重用已归档 ID，目录和阶段由 `ai-gate.sh status <ID>` 解析。`MEMORY.md`、路线图等参与代码指纹的文件在最后一次正式 G4 前更新，归档时只复核。指南不得把示例事实当作真实架构，也不复述 `harness/redlines.conf` 的可变阈值数字，只引用配置键。
- **验证**：①可用单步紧凑记录；②③在 G3 提前列边界样本，G5 独立审查仍保留。首次正式 G4 前对照原文锚点、AC、设计文件清单与 Git 状态检查非流程交付物，运行未暂存和已暂存 diff 的空白校验；交付物或暂存状态随后变化则重验。正式 G4 的目标须是归档后路径与内容稳定的项目文件；验证器拒绝以 `process/specs/**`、`process/metrics.md` 或 `process/task-pool/**` 为正式目标。②③的 G6 一律要当次结果决定；`acceptance.md` 每项以「通过」开头，`code-review.md` 负责核对 AC 措辞与证据和结论是否一致。检查指南命令与门禁实现一致。
- **需求语义与审查**：②③记录易走样的原文锚点，设计矩阵覆盖 REQ/ERR/AC，任务引用设计章节。独立审查用 `ai-resume.sh review <feat> <base-ref>` 定位原文、完整相关 diff、验证摘要、相关知识与本次改动的 AI 协作文件；机器只查记录完整，语义由审查判断。
- **结果与前提**：新需求记录完成后希望促成的行动、效果和观察方式；设计自审从原始材料低成本证伪关键前提。AC 可用命令、报告或可观察输出作证据；实际用户效果在交付后回访，不由测试通过推定。有证据的后续问题只作候选，维护者提出或确认后才进入任务池。
- **设计审查、复用与记忆**：②③在 pass g3 前由未写方案的上下文只读审查设计并记入 design.md §5；任何宿主都可用新会话、另一工具或 subagent 完成，不依赖宿主专属 hook。设计 §4 记录复用检索。记忆捕获与纠正替换写在 `AGENTS.md` §3、晋升写在 `gc-memory.md`：`MEMORY.md` 属项目事实、不随 upgrade 替换，只留指针。AI 只把新增常驻规则写成建议交维护者决定。
