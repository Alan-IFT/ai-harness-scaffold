# 项目指南

- **范围**：`template/AGENTS.md`（规则入口）、`template/.agents/skills/`（按阶段读的指南）、Spec 模板与 `README.md`。
- **为什么只写一份入口**：各 AI 工具都能读 `AGENTS.md`，`CLAUDE.md` 只做导入；规则写两份就会分叉。
- **为什么保留只有一行导入的 `CLAUDE.md`**：Claude Code 新版能直接读 `AGENTS.md`，但默认只在工作目录及上级都没有 `CLAUDE.md`、`CLAUDE.local.md` 时才读，有些会话还读不到。删掉它只省一行，用户一加 `CLAUDE.local.md` 放个人说明，规则就整份不再加载；留着这行导入，各种情况都读得到，也不会读两遍。依据是官方文档 `code.claude.com/docs/en/memory`（2026-11-10 复核），再提议删除前先看它当时的说法。
- **为什么指南只引用配置键**：阈值以项目自己的 `harness/redlines.conf` 为准，指南里写死数字会和配置不一致。
- **为什么方案并进 tasks.md、人的决定并进 review.md**：`design.md` 与 `acceptance.md` 只被格式检查读过，真实缺陷都由独立审查发现（ADR-0003）。
- **为什么「需人决定：是」要先审方案**：编码后再推翻方案代价最高；任何宿主都能用新会话或 subagent 做这一步。
- **为什么审查者要复核「需人决定」、对照记忆与模块活文档、只拦本次引入或加重的问题**：「需人决定」是 g3 要人当次决定的唯一开关，却由写方案的 AI 在 g1 自判、不进状态指纹；项目记下的坑不在审查者眼前，改动让文档说谎就没人发现；老问题挡门会逼实现者改需求外的代码。审查后才改为「是」的不补审方案：g3 现读该字段、要人当次决定，代码已写完再审方案只是走形式。取自 Claude Code 团队的审查实践（2026-10-30 评估）。
- **为什么编码原则用 Karpathy 准则原文**：维护者 2026-10-25 定下吸收原文，重复处以它为准，与流程、红线有歧义时交人决定；同一说法只留一处，指南不复述 AGENTS.md。
- **为什么个人偏好单独放 `PREFERENCES.md` 且不入库**：语言、语气这类习惯因人而异，写进 `MEMORY.md` 会变成全队的“项目事实”；不入库也就不进状态指纹，改偏好不会让验证过期。
- **为什么通用偏好放 `~/.ai-harness/PREFERENCES.md`**：宿主自带的偏好注入只对那个宿主生效，换工具就丢；写进 `AGENTS.md` 的读取规则对所有工具都有效，一份文件跨项目共用。目标项目不知道脚手架仓库在哪，所以放用户目录而不是脚手架仓库里。
- **为什么写明 AI 工具自带的记忆不作来源**：工具会把经验记进自己的记忆目录，换一个工具接手就读不到；2026-11-09 核对本仓库时，就有几条经验只存在 Claude Code 的记忆里。不宜入库的项目事实没有别的位置，所以放进不入库、每次接手又都会读的 `PREFERENCES.md`，不另开文件。
- **为什么小改动的出口只列源码注释和说明文档**：本仓库的 `AGENTS.md` 早有「非平凡变更走三道门」，模板里却没有对应的话，界线全凭各工具自己判断。只放行列得出的：规则、指南、配置、Spec 模板和脚本里的字符串，措辞就是行为，列「除外」清单总会漏。有活跃 Spec 时不放行，因为状态指纹按全仓算，一次小改动就会让它的验证过期。
- **为什么 README 讲结构不抄规则**：只有安装说明时，读者判断不了项目是什么、怎么运转（维护者 2026-11-06）。README 写问题、流程、架构和脚本与配置的总览；门的完整规则和操作步骤留在 `template/AGENTS.md` 与指南，避免两边分叉。英文版只做摘要，因为产出的规范都是中文。
- **改动时**：同步检查 `skill/SKILL.md` 与自检，确保指南里的命令与脚本一致。
