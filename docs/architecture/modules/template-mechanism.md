# 模板机制

- **范围**：`template/scripts/`、`template/harness/`、`template/process/specs/_templates/`。根目录 `scripts/` 只转发。
- **为什么门只查骗不过的信号**：字段已填、命令跑过、状态指纹一致这类检查不会误报；措辞与方案质量交给独立审查和人（ADR-0003）。
- **为什么状态指纹全仓计算、只排除 `process/`**：按文件清单的局部指纹依赖人工确认依赖，容易漏；流程记录集中在一个目录，排除一处即可。
- **为什么状态指纹只在 Git 仓库里算**：全仓指纹靠 Git 的索引、差异和忽略规则。原来在没有 Git 仓库、或 Git 因目录归属等原因读不了仓库时，会悄悄退回到只算验证目标那一个文件，改别的文件不会让验证过期。那里没有忽略规则可用，不值得另写一套全目录哈希，所以直接报错，并保留 Git 自己的报错好看出是哪种情况；接入说明本来就要求先 `git init`。自检沙箱因此也建成 Git 仓库，否则前 8 节测的是那条退路。
- **为什么任务池用目录锁**：`archive` 与 `start-next` 可能被两个会话同时调用，锁保证只有一个活跃 Spec 被创建。
- **为什么归档要复核三道门**：归档前没有校验时，跳过 g2/g3 直接归档也能成功；归档时再跑一次 g3 检查，也拦住了审查通过后又改代码的情况。
- **为什么正式验证不带目标文件、却导出 `SPEC_NAME`**：一个目标文件代表不了一次改动。按 `$TARGET_FILE` 分派检查时，查什么取决于挑了哪个文件，挑一个容易过的也能拿到 PASS；当初要求目标写在「涉及文件」里只堵了一半。检查默认对整个项目生效，状态指纹也是全项目的。但核对过的三个接入项目都靠目标文件分派增量检查（整项目检查太慢，或要外部数据库），所以留一条替代的路：检查命令按 `$SPEC_NAME` 读该 Spec 的全部「涉及文件」来分派。
- **为什么任务池只留 AI 用的命令**：维护者只用自然语言提需求；补充需求、指定优先这类事由 AI 直接改任务文件（`- 优先: 是`），不再需要专门的子命令和 `NEXT` 文件。编号同时避开已归档的任务文件和 `feat-t-*` 目录：任务可以关联到别的名字的 Spec，任务文件也可能被删而 Spec 目录还在。
- **为什么任务文件随 Spec 归档**：留在池里时，`next`、`list`、`add` 每次都要逐个读一遍，Git Bash 起进程慢，300 个已归档任务时分别要 38、93、21 秒；池里只留没做完的，耗时不再随历史增长（同样条件下都在 1 秒内）。关联的 Spec 不在 active 的任务在 `list` 里显示「关联异常」，升级前遗留的已归档任务文件靠它发现。
- **为什么验证只认 `verify.conf` 的一条命令**：自动探测工具链在老项目里经常选错；由接入时的 AI 选一条真实命令更可靠。
- **locale**：宿主 shell 可能没有 UTF-8 locale。多字节字符不放进 `[]` 字符类；全角冒号与全角空格在取字段值前归一，自检用 `LC_ALL=C` 复跑。
