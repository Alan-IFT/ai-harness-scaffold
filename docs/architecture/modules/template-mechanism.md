# 模板机制

- **范围**：`template/scripts/`、`template/harness/`、`template/process/specs/_templates/`。根目录 `scripts/` 只转发。
- **为什么门只查骗不过的信号**：字段已填、命令跑过、状态指纹一致这类检查不会误报；措辞与方案质量交给独立审查和人（ADR-0003）。
- **为什么状态指纹全仓计算、只排除 `process/`**：按文件清单的局部指纹依赖人工确认依赖，容易漏；流程记录集中在一个目录，排除一处即可。
- **为什么状态指纹只在 Git 仓库里算**：全仓指纹靠 Git 的索引、差异和忽略规则。原来在没有 Git 仓库、或 Git 因目录归属等原因读不了仓库时，会悄悄退回到只算验证目标那一个文件，改别的文件不会让验证过期。那里没有忽略规则可用，不值得另写一套全目录哈希，所以直接报错，并保留 Git 自己的报错好看出是哪种情况；接入说明本来就要求先 `git init`。自检沙箱因此也建成 Git 仓库，否则前 8 节测的是那条退路。
- **为什么指纹脚本给 `git diff` 关掉换行提示（`-c core.safecrlf=false`）**：工作区有 CRLF 文件、仓库又统一成 LF 时，Git 往错误输出写一行警告；门禁状态把校验的错误输出一起收进「阻断原因」，这一行就排在真正的原因前面。在源头关掉，调用指纹脚本的各处都不再有它；不在门禁里丢掉错误输出，是因为指纹算不出来时的报错也走那里。这个参数只关提示、不改 diff 的内容，指纹值不变（feat-t-000056 用同一个工作区前后各算一次核对过）。
- **为什么任务池用目录锁**：`archive` 与 `start-next` 可能被两个会话同时调用，锁保证只有一个活跃 Spec 被创建。
- **为什么并行是「多开工作区」而不是放开「一次一个 Spec」**：状态指纹全仓计算，两个 Spec 在同一个工作区里做，谁的验证都对不上自己的改动；一个工作区一个 Spec 时，现有的门不用改。命令不变，脚本只多认一件事：自己在哪个工作区。
- **为什么任务池全仓库只有主工作区那一份**：任务文件是入库的，每个工作区各有一份副本时，两边各收录一条会编成同一个号，一边领了任务另一边看不见，锁也各管各的（2026-11-27 沙箱实测）。只留一份，编号、认领、锁就都只有一处。代价是在别的工作区里收录或领取，改的是主工作区的文件，改动留在那里等下一次提交。
- **为什么 Spec 的归属这样判**：别的工作区从主线分出时会带着主线在途 Spec 的目录副本，不排除它就领不了自己的任务，所以「和主工作区的分叉点里已经有的不算」。先在主工作区启动、再挪到别的工作区做的 Spec 用这一条认不出来，所以再认一条「分支名等于 Spec 名的工作区是它的主人」（维护者 2026-11-27 定，本机一个接入项目当天就是这样用的）。同名分支的工作区里得真的有这个目录才算挪走了，免得没提交就开工作区、或目录被手动删掉时没人认它。分支名不同于 Spec 名的工作区合入主线后，Spec 归主工作区：快进之后历史里分不出它是在哪启动的。
- **为什么归档只在主工作区做**：归档时的 g3 复核是合入之后的最后一道检查，要在主线的实际状态上判。允许在别的工作区里归档时，两条线各自验证通过、先后合入，合在一起检查失败，而两个 Spec 都已归档，没有门再拦（2026-11-27 用原样脚本复现）。
- **为什么正式验证全仓库同一时间只跑一个，而且始终加锁**：几个工作区共用本机的端口、数据库和内存；两个会话同时验证时后跑的那个失败，还被记成一次连续失败，离触顶停下更近（沙箱里一个会话连败 2 次，上限 3）。只在有多个工作区时才加锁会留一个空档：主工作区正在验证时新开工作区。锁里记进程号，进程不在了就作废，因为宿主的命令超时在 Windows 上是强杀，来不及删锁。不设等待上限：上限是阈值，阈值只放红线配置；等待提示里给了进程号和锁文件位置。两个等待者同时清理同一把残留锁时，仍可能让一次验证相撞。锁只管 `ai-verify.sh`，直接跑检查命令不受它管。
- **为什么 `status` 在三道门齐了以后还要复核一次**：有多个工作区时，别的线先合入会让一条已经过完门的线过期；只看 `.gates` 就会一直显示「可归档」，接手的人和 AI 都会被它带偏。
- **有多个工作区时已知而不处理的**：主工作区有没提交的代码改动时把别的线快进进来，归档会被拒，那个 Spec 留在主工作区的 active 里，等主工作区提交后重新验证；用 `git rebase` 同步的那段时间里，那条线的 Spec 目录暂时不在工作区里，主工作区会把它的任务显示成「关联异常」；从别的工作区再开工作区，两边会都认上一条线的 Spec；主工作区是裸仓库的布局不支持；`harness/redlines.conf` 和 `harness/verify.conf` 各工作区读自己的副本。让 `archive` 代做合入、任务池的锁改成等待都先不做，触发条件记在 feat-t-000059 的任务文件「目前的方向」一节（归档后在 `process/specs/archive/` 下）。
- **为什么归档要复核三道门**：归档前没有校验时，跳过 g2/g3 直接归档也能成功；归档时再跑一次 g3 检查，也拦住了审查通过后又改代码的情况。
- **为什么正式验证不带目标文件、却导出 `SPEC_NAME`**：一个目标文件代表不了一次改动。按 `$TARGET_FILE` 分派检查时，查什么取决于挑了哪个文件，挑一个容易过的也能拿到 PASS；当初要求目标写在「涉及文件」里只堵了一半。检查默认对整个项目生效，状态指纹也是全项目的。但核对过的三个接入项目都靠目标文件分派增量检查（整项目检查太慢，或要外部数据库），所以留一条替代的路：检查命令按 `$SPEC_NAME` 读该 Spec 的全部「涉及文件」来分派。
- **为什么任务池只留 AI 用的命令**：维护者只用自然语言提需求；补充需求、指定优先这类事由 AI 直接改任务文件（`- 优先: 是`），不再需要专门的子命令和 `NEXT` 文件。编号同时避开已归档的任务文件和 `feat-t-*` 目录：任务可以关联到别的名字的 Spec，任务文件也可能被删而 Spec 目录还在。
- **为什么任务文件随 Spec 归档**：留在池里时，`next`、`list`、`add` 每次都要逐个读一遍，Git Bash 起进程慢，300 个已归档任务时分别要 38、93、21 秒；池里只留没做完的，耗时不再随历史增长（同样条件下都在 1 秒内）。关联的 Spec 不在 active 的任务在 `list` 里显示「关联异常」，升级前遗留的已归档任务文件靠它发现。
- **为什么验证只认 `verify.conf` 的一条命令**：自动探测工具链在老项目里经常选错；由接入时的 AI 选一条真实命令更可靠。
- **locale**：宿主 shell 可能没有 UTF-8 locale。多字节字符不放进 `[]` 字符类；全角冒号与全角空格在取字段值前归一，自检用 `LC_ALL=C` 复跑。
