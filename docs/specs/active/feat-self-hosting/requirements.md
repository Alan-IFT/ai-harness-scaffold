# 需求与验收规范：feat-self-hosting

- 创建时间：2026-10-20
- 状态：实现中
- 需求来源：仓库维护者要求本项目使用自己发布的脚手架，并进行 Git 初始化。
- 原始问题 / 原话：用户提出「本项目自己本上能用上这个脚手架吗？若可以，则本项目也用这套脚手架，并进行git初始化」。
- 需求分级（象限）：② 人机协同·风险侧；现有仓库已经有历史和未提交改动，必须保留；维护者决定风险与结果，Agent 执行核验并留痕。
- 分级依据：代码体量较小，但自用配置必须与分发模板隔离；Git 历史及当前改动不得受损。

## 0. 必须明确
- 做什么：让本仓库用项目内 Spec、门禁、验证、接力文件管理后续开发。
- 为谁做：在 Claude Code、Codex 等工具间切换的本仓库维护者。
- 关键业务规则：模板机制只维护一份；根目录只建薄入口和本仓库状态；已有 Git 仓库及未提交改动保持原样。
- 验收标准：根目录可执行恢复、建 Spec、门禁、自检与验证命令；没有重复模板脚本；Git 历史保持连续。

## 1. 背景与范围
- 仓库包含 bin/、skill/、template/，之前只有分发给其他项目的模板，没有本仓库自己的接力状态。
- 本次新增根目录的项目规则、架构索引、配置与薄转发脚本，并用本 Spec 记录工作。
- 不迁移历史提交，不复制 template/scripts 的实现；G6 不冒充维护者执行过检查或读过全部材料。

## 2. 结构化需求
- REQ-01：当 Agent 从根目录接手时，应能读取本仓库的 AGENTS.md、当前 Spec、Git 改动并运行恢复命令。
- REQ-02：当根目录执行脚手架命令时，应调用 template/scripts 的单一实现，并把状态写进根目录项目文档。
- REQ-03：当发现 Git 已初始化时，应保持现有 main 分支、历史提交与未提交改动。
- REQ-04：当进入 G6 时，Agent 应自行运行检查并整理证据，将维护者对关键结果的明确决定和来源写入记录后推进，无需维护者填写文档或执行冒烟命令。
- ERR-01：当本仓库验证没有执行真实检查时，必须失败，不能产生 PASS 摘要。

## 3. 验收标准
| 编号 | 验收点 | 通过条件 | 不通过条件 | 量化指标 / 证据 |
| :-- | :-- | :-- | :-- | :-- |
| AC-01 | Git 状态 | 原 HEAD、main 分支及原有改动均保留 | 历史重建或原有改动丢失 | git rev-parse、git status 前后对照 |
| AC-02 | 单一机制 | 根目录脚本只转发到 template/scripts | 根目录另有机制副本 | 逐个检查 scripts/ 内容 |
| AC-03 | 自用流程 | 根目录可建 Spec、看状态、恢复、验证 | 任一命令缺少依赖而失败 | 实际运行命令及验证摘要 |
| AC-04 | 跨 IDE 接力 | AGENTS.md、tasks.md、verification.md 与 Git 保存状态 | 状态只留在宿主会话 | 文件存在且恢复快照可读取 |
| AC-05 | 分工验收 | Agent 的检查与维护者的决定分别留痕 | 把 Agent 的运行写成维护者亲测 | acceptance.md 与 G6 校验 |

## 4. 待确认问题
- [x] Q1：是否新建 Git 仓库？已确认现有仓库在 main，含历史提交；保持原状即可。
- [x] Q2：是否复制模板脚本到根目录？采用薄转发，避免第二份机制。

## 5. 非功能约束
- 脚本保持 Bash + Git Bash 可用，不绑定 IDE。
- 本地报告和红线哈希不入库；可交接摘要进入 Git。
- 自检不应改动本仓库的业务内容；测试沙箱使用临时目录。
