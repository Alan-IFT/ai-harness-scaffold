# 需求与验收规范：feat-t-000004

- 状态：Approved
- 需求来源：`docs/task-pool/T-000004.md`
- 原始问题 / 原话：「那就按照建议做」；前文建议为 G4 前核对交付物和语义、完整验证分段计时、quick 相关检查、补暂存区 diff 校验。
- 需求分级（象限）：② 人机协同·风险侧；改动验证配置和分发指南，错误跳过检查会影响后续交付。
- 分级依据：实现是局部 Bash 和文档，复杂度较低；验证覆盖和下游指南传播有风险。

## 0. 必须明确

- 做什么：改进本仓库验证效率和可诊断性，补上暂存区空白错误检查与正式验证前准备指引。
- 为谁做：本仓库维护者与使用脚手架的 Agent。
- 关键业务规则：正式 G4 仍执行全自检和 CLI 回归；quick 只作开发反馈，不生成 G4 摘要；时间数据用于识别慢阶段，不据猜测并行化。
- 验收标准：分段耗时可见、两类 diff 均被检查、quick 对目标文件有相关检查、指南说明正式 G4 前的核对顺序，回归通过。

## 1. 背景与目标

- 背景：前一任务的正式验证耗时约四分钟，单个 CUSTOM_CHECK 隐藏各阶段成本。暂存后的空白错误可绕过目前的 git diff --check。
- 完成后的行动与效果：维护者能从日志定位耗时阶段，并在 G4 前发现交付物或语义遗漏。基线为最近一次完整验证约 254 秒；首次计时只作基线，不承诺本次缩短固定百分比。
- Non-Goals：不削弱 G4，不重构自检共享夹具，不改人类专属 redlines.conf，不让项目专属检查进入分发模板。

## 2. 结构化需求

- REQ-01: WHEN 本仓库运行完整验证，THE SYSTEM SHALL 保留全自检与 CLI 回归，并分别输出每阶段耗时和结果。
- REQ-02: WHEN 运行 quick 或完整验证，THE SYSTEM SHALL 检查未暂存及已暂存 diff 的空白错误。
- REQ-03: WHEN 运行 quick 且目标为 Shell、CLI 或项目指南，THE SYSTEM SHALL 执行与目标相关的短检查，并保持 quick 不生成 G4 摘要。
- REQ-04: WHEN Agent 准备首次正式 G4，指南 SHALL 提醒核对交付物、文件清单及需求语义，再运行完整验证。
- ERR-01: IF 任一正式验证阶段失败，THEN THE SYSTEM SHALL 返回失败并标明失败阶段。
- ERR-02: IF 暂存区有空白错误，THEN quick 和正式验证 SHALL 失败。
