- **创建时间**: 2026-10-23
- **状态**: Approved
- **需求来源**: `docs/task-pool/T-000027.md`（原始需求与更新）
- 原始问题 / 原话：见 `docs/task-pool/T-000027.md`：维护者「那就是架构设计问题？需要优化架构，而不是在这里不断的修修补补」「那就按照建议的方向走」——暂停补丁式任务，先做架构评审，再按结论重新分诊任务池。
- 需求分级（象限）：③ 人机协同·复杂度侧；涉及流程状态布局、指纹模型、门禁判定方式与验证结构四处架构取舍，须由维护者拍板拆分。
- 分级依据：复杂度来自四个问题相互耦合（如流程状态放哪决定指纹模型与任务池结构）；本 Spec 只产出决策与迁移方案，不改脚本，风险低。

## 0. 必须明确（四项，缺一项不得进入设计）

- 做什么：写一份架构决策记录（ADR），对流程状态布局与指纹模型、自然语言门禁判定、验证结构、任务池分诊四个问题各给出现状证据、2~3 个备选方案与代价、推荐项，经独立审查后由维护者逐项拍板；再给出分阶段迁移顺序，并按决定重新分诊现有待办。
- 为谁做：本仓库维护者（做架构决定）与后续接手的 Agent（按 ADR 执行迁移，不再零散补丁）。
- 关键业务规则：每个问题的结论由维护者明确决定，Agent 不替人拍板；本 Spec 不修改 `template/`、`bin/`、`scripts/`；每个待办在分诊后都有明确去向（保留、合并、作废或改为顺手修），队列状态随之改写（保留 → 待办，合并 / 作废 → 取消，顺手修 → 暂缓），作废须写理由；迁移阶段缺少入口任务时在本 Spec 内收录。
- 验收标准：ADR 四个问题都有证据、方案、代价、推荐与维护者决定；迁移方案列出阶段、每阶段的入口任务与回滚方式；T-000015~T-000026 与 T-000028 每条都有分诊结论、补充记录与相应队列状态，`docs/task-pool/NEXT` 指向第一个迁移阶段的入口；独立审查无关键问题。

## 1. 业务背景与目标 (Context & Goal)
- **背景**：T-000005 起 10 个 Spec 几乎都在修补门禁边角，任务由上一 Spec 的审查建议繁殖，正式验证从 215 秒涨到 376 秒（自检第 2、3 节占 222 秒）；独立根因分析指出四个结构性问题。
- **完成后的行动与效果**：维护者据 ADR 决定迁移路线；后续 Spec 按迁移阶段推进。基线：待办 13 条（T-000015~T-000026 与 T-000028），近 10 个 Spec 中 9 个有 G4 回退（累计 11 次）；回访信号为迁移后同类边角任务不再产生、正式验证耗时下降。
- **Non-Goals（本次明确不做）**：
  - 不实施任何迁移代码；不修改门禁脚本、CLI 与模板文件；不删除待办任务原件（只追加补充并改写队列状态字段；脚本暂无改状态的子命令，按字段手工改写）。

## 2. 结构化需求 (EARS Acceptance Criteria)

### 2.1 正常流 (Happy Paths)
- **REQ-01**: WHEN 维护者阅读 ADR，THE ADR SHALL 对四个问题分别给出现状证据（文件路径或数据）、至少 2 个备选方案及代价、一个推荐项。
- **REQ-02**: WHEN 维护者对某问题作出决定，THE ADR SHALL 记录决定内容、决策人与原话来源。
- **REQ-03**: WHEN 四个问题都有决定，THE ADR SHALL 给出分阶段迁移顺序，每阶段写明入口任务、依赖与回滚方式。
- **REQ-04**: WHEN 迁移方案确定，每个待办（T-000015~T-000026 与 T-000028）SHALL 得到保留、合并、作废或改为顺手修之一的结论，写进其任务文件补充记录并改写队列状态；缺少入口任务的迁移阶段 SHALL 在本 Spec 内收录，`docs/task-pool/NEXT` SHALL 指向第一个阶段的入口，其余阶段入口 SHALL 为暂缓。

### 2.2 异常与边界流 (Edge Cases & Error Handling)
- **ERR-01**: IF 维护者对某问题未作决定，THEN 该问题 SHALL 标为待定，迁移方案不得包含依赖它的阶段；IF 四个问题全部待定，THEN 本 Spec SHALL 判为不通过。
- **ERR-02**: IF 某待办被作废，THEN 补充记录 SHALL 写明理由与对应的 ADR 决定。
