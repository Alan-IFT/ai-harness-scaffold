# 需求与验收：feat-flow-closure

- 需求来源：用户授权按文章审查建议改造本脚手架。
- 原始问题 / 原话：用户说「那就按照推荐做」，指上一轮文章图文审查列出的四项改进与交付反馈。
- 需求分级（象限）：③人机协同·复杂度侧；跨模板、门禁和自检修改。
- 分级依据：无生产数据风险；模板与脚本的一致性带来中等复杂度。

## 0. 必须明确（四项）
- 做什么：增加轻量需求入口、象限分流、间接影响核对、知识相关性与失效检查、按风险交互验收和交付反馈。
- 为谁做：使用本脚手架并跨 IDE 接力的开发者与 AI Agent。
- 关键业务规则：状态保存在项目 Markdown 与 Git；④只分析移交；①可精简设计；②③须有人的前置判断；不增加宿主依赖。
- 验收标准：见第 3 节 AC 表，正反例自检须通过。

## 1. 背景与目标
现有开发阶段完整，但需求入口、真正的象限执行、间接影响和知识失效仍有缺口。目标是在原有模板和脚本上补齐，不建平台。

## 2. 结构化需求
- REQ-01：WHEN 有粗想法，THE PROJECT SHALL 在项目文档保留原始问题、处理决定和 Spec 链接。
- REQ-02：WHEN 选择④，THE HARNESS SHALL 阻止 G2 及后续自动开发门。
- REQ-03：WHEN 选择①，THE HARNESS SHALL 允许单项可验证切片；②③须记录人的前置决策。
- REQ-04：WHEN 设计变更，THE SPEC SHALL 记录间接消费者与检索依据。
- REQ-05：WHEN 注入知识，THE HARNESS SHALL 拒绝过期或待验证卡，支持按模块推荐和按变更路径提示复核。
- REQ-06：WHEN 功能交付，THE PROJECT SHALL 能记录发布状态、实际反馈和阶段等待时间。
- REQ-07：WHEN 进入 G6，THE AGENT SHALL 自行运行冒烟或增量验证并写入客观证据；①可依据证据自动收尾，②③仅向人提出需要判断的风险与结果，收到明确决定后由 Agent 记录并推进，不要求人编辑 Markdown、运行命令或逐一阅读所有材料。④仍在 G1 后移交。

## 3. 验收标准
| 编号 | 验收点 | 通过条件 | 不通过条件 | 量化指标 / 证据 |
| :-- | :-- | :-- | :-- | :-- |
| AC-01 | 需求入口 | 可保留原话、决定、Spec 链接 | 只有 AI 摘要 | 模板内容 |
| AC-02 | 象限路由 | ④挡住 G2；①单步可过；②③有前置决策 | ④仍能自动开发 | 门禁自检正反例 |
| AC-03 | 影响核对 | 设计记录消费者及检索范围 | 只有文件清单 | G3 正反例 |
| AC-04 | 知识复核 | 检索留依据；旧卡不得注入；路径变更提示复核 | 过期卡被直接使用 | 脚本自检 |
| AC-05 | 交付反馈 | 记录发布、反馈和等待时间 | 合并即结束 | 模板与度量核对 |
| AC-06 | 跨宿主 | 项目文档与 Bash 可接力 | 依赖 IDE 状态 | CLI dry-run、自检 |
| AC-07 | 分工验收 | ①有客观证据可由 Agent 推进 G6；②③有人的明确决定及来源，Agent 记录执行环境与证据后推进 | 伪称人执行命令、伪称已读四类材料或无决定直接通过 | G6 正反例与两项实际验收记录 |

## 4. 待确认问题
- 已确认：用户 维护者 作为管理员与架构协作者审查关键结果和风险，不亲自承担每项冒烟执行与文档填写；Agent 执行验证并留痕。

## 5. 非功能性约束
- 不覆盖已有用户项目文件；不新增云端服务或 IDE 插件依赖；本地门禁不冒充身份验证。
