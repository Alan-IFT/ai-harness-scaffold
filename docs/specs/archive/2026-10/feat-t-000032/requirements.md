## 0. 必须明确（四项，缺一项不得进入设计）

- 做什么：按 ADR-0002 §3.2 删除 D1~D6 的代码、模板字段、指南段落、配置键与自检用例；G6 三处改为只认行首结构化结论「通过」；`code-review.md` 增加含糊词与「证据与结论矛盾」检查项；`upgrade` 处理模板已删除的托管文件；README、模块活文档与本仓库自用状态同步。
- 为谁做：安装本脚手架的下游项目及其 Agent（任意宿主），以及本仓库维护者。
- 关键业务规则：只删 ADR-0002 决定删除的项，保留项（K1~K16）行为不变；G3 记录仍写 5 列以保持 G5 审查状态绑定；`upgrade --dry-run` 保持只读；本地修改过的已删除文件不得被自动删除；不修改根目录 `harness/redlines.conf`（只允许人类修改）。
- 验收标准：门禁、模板、指南、CLI 中不再出现 D1~D6 的机制；G6 用结构化结论判定；自检与升级回归全部通过且自检耗时下降；下游升级能删除未改动的已删除托管文件并报告改动过的文件。

- **背景**：ADR-0002 统计：门禁正则只留下误报，条件委托与 `--by human` 使用 0 次，知识卡全仓 1 张，可行性评分是同一 Agent 自评；正式验证 363 秒、自检 258 项。
- **完成后的行动与效果**：下游升级后 Agent 少填评分表、知识注入与委托字段，G2/G6 不再因措辞被误拦。回访信号：`ai-gate.sh` 与 `harness-selftest.sh` 行数、正式验证耗时较 821 / 1161 行、363 秒下降。
- **Non-Goals（本次明确不做）**：
  - 不迁移流程记录目录、不改状态指纹（R2，T-000033）。
  - 不改任务池行为；不发布版本（R2 归档后一起发布）。

## 2. 结构化需求 (EARS Acceptance Criteria)

### 2.1 正常流 (Happy Paths)
- **REQ-01**: WHEN G2 校验 requirements.md，THE 门禁 SHALL 只检查 AC 编号、「不通过」条件与无空单元格，不扫描措辞。
- **REQ-02**: WHEN G6 校验 acceptance.md，THE 门禁 SHALL 要求「冒烟或 E2E 证据」「对照 AC 的检查结果」与每条 `AC-xx` 的值以「通过」开头，后接证据文本不扫描。
- **REQ-03**: WHEN G1 校验 requirements.md，THE 门禁 SHALL 不再要求可行性评分表与 `FEASIBILITY_MIN`，其余四项必答、原话、待确认、象限与分级依据检查不变。
- **REQ-04**: WHEN ②③ Spec 推进 G3 与 G6，THE 门禁 SHALL 不再识别条件委托；G6 一律要求当次「人工决定：通过」；G3 记录仍为 5 列。
- **REQ-05**: WHEN Agent 推进 G4 或运行 doctor / resume / new-spec，THE 脚手架 SHALL 不再要求或调用知识卡（`ai-knowledge.sh`、`.knowledge/`、「注入知识」「知识检索」字段、`KNOWLEDGE_TTL_DAYS`）。
- **REQ-06**: WHEN 调用 `ai-gate.sh pass`，THE 命令 SHALL 不再接受 `--by`，记录者恒为 agent。
- **REQ-07**: WHEN 独立审查者按 `code-review.md` 审查，THE 清单 SHALL 包含 AC 含糊措辞与验收证据和结论矛盾两项检查。
- **REQ-08**: WHEN 下游执行 `upgrade`，THE CLI SHALL 删除 manifest 记录且与记录哈希一致、但模板中已不存在的托管文件，并报告与记录不一致的此类文件而不删除；`--dry-run` 只报告。

### 2.2 异常与边界流 (Edge Cases & Error Handling)
- **ERR-01**: IF 在途 Spec 的 acceptance.md 仍为旧格式（AC 行不以「通过」开头），THEN G6 SHALL 拒绝并提示按新格式改写。
- **ERR-02**: IF 下游已删除托管文件被本地修改过或经 `--accept-custom` 定制，THEN upgrade SHALL 保留文件、列出路径并以非零状态提示人工处理。
