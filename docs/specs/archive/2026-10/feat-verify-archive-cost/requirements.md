# 需求与验收规范：feat-verify-archive-cost

- 创建时间：2026-10-20
- 状态：Approved
- 需求来源：用户在 feat-delivery-speed 归档后要求单独检查两个耗时点
- 原始问题 / 原话：「那就看看这两个耗时点，是否能单独优化」
- 需求分级（象限）：③ 人机协同·复杂度侧；涉及自检性能取舍和跨工具归档规则
- 分级依据：盲目删门禁检查会产生错误通过；归档元数据与代码指纹的边界需保持一致

## 0. 必须明确（四项）
- 做什么：实测完整门禁自检是否可安全提速，并消除归档改写入口表造成的二次正式验证
- 为谁做：维护本脚手架和使用它的项目团队
- 关键业务规则：不得为了提速降低完整自检或 G4/G5 覆盖；需求入口只记全生命周期唯一的 Spec ID，阶段和目录位置由门记录解析；知识卡、路线图等参与代码指纹的文件须在最后一次正式 G4 前完成
- 验收标准：记录可复测的自检剖析与优化试验结论；归档不需改写需求入口中的目录状态，已归档 Spec 仍能按 ID 查到

## 1. 背景与目标
前一 Spec 的完整自检 121/121，两次正式验证各耗时 137 秒。归档时把 `docs/INTAKE.md` 的链接从 active 改为 archive，又使 G4 摘要过期，被迫第二次正式验证。分段计时显示自检第 3 段耗时 64 秒；尝试前移 G6 材料拒绝后该段为 61 秒，但新增必要反例使总耗时约 139 秒，因此已撤回该试验，不将其当作提速成果。

- Non-Goals：不降低 G4 的正式验证覆盖，不提高 120 秒提醒线，不加入宿主专属状态或缓存数据库，不重写所有门禁。

## 2. 结构化需求
- REQ-01：WHEN 评估完整自检提速，THE HARNESS WORKFLOW SHALL 先量化各段耗时，再只保留有可复测总收益且不减覆盖的实现；无收益的试验撤回。
- REQ-02：WHEN 创建 Spec 并在需求入口登记，THE HARNESS GUIDANCE SHALL 用全生命周期唯一的 Spec ID 关联；已归档 ID 不得重用；WHEN 归档，SHALL 从该 ID 查门记录和位置，无需改写入口记录。
- REQ-03：WHEN 运行正式自检，THE HARNESS SHALL 保留原有全部正反例与 120 秒提醒线。
- REQ-04：WHEN 归档流程需要维护知识卡、路线图或其他参与指纹的文件，THE HARNESS GUIDANCE SHALL 在最后一次正式 G4 前完成更新；正式验证不得以归档时会移动或更新的流程文件为 target；若 G5/G6 才发现必须修改，SHALL 重跑正式 G4 与后续门。
- ERR-01：IF 提速试验降低检查数或总耗时无改善，THEN SHALL 不把试验合入机制。
- ERR-02：IF Spec 从 active 移到 archive，THEN 入口关联 ID SHALL 保持有效且无需同步路径副本；后续新建不能复用该 ID。

| 编号 | 验收点 | 通过条件 | 不通过条件 | 量化指标 / 证据 |

| AC-02 | 完整自检不降级 | 原有 121 项全部保留，120 秒提醒线不改 | 为提速删覆盖、改阈值或仅跑 quick | 正式完整验证 |

- 兼容与迁移：旧入口行可迁为 ID；旧 Spec 和原有 gate CLI 参数不变。
