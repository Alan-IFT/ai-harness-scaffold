- 原始问题 / 原话：你怎么看这个方案：《多需求并行开发方案（供评审）》，我觉得有更完美的方案，是可以做到的。（评判标准的原话：「脚手架独立于宿主，且功能是好用、必要且不臃肿的」。六轮讨论里维护者的每次答复、最后的「那就按照推荐做吧」和「认（推荐）」，都记在任务文件「补充与变更」；每一轮的提议和实测记在任务文件「需求讨论」）
- 需人决定：是，改规则入口和脚本行为，并且改变有多个工作区时任务池和归档的行为（架构取舍）

## 1. 要做什么
- 做什么：让脚手架支持多个需求并行。一个工作区同一时间只做一个 Spec，要并行就多开 Git 工作区，命令不变；脚本负责能机械判定的几件事（见验收标准），怎么开工作区、怎么合回主线写成一份按需读的指南。
- 为谁做：用本脚手架的维护者和接手的 AI 会话。需求只能一个个排队太慢，想并行又怕冲突、管理复杂、容易出问题。
- 不做：
  - 不加命令、配置键、Spec 字段；不要求工作区的分支必须起成 Spec 名（同名分支只是「把已经启动的 Spec 挪出去做」时的判据）。
  - 脚本不执行 Git 的写操作：建工作区、同步、合入、删工作区都由 AI 用 Git 做。
  - 不改 g3「审的是当前验证状态」的判定。任务文件里记了触发条件的几项这次都不做：`archive` 代做合入、「改动指纹」、任务池的锁改成等待、工作区数量上限、`MEMORY.md merge=union`。
  - 不管宿主怎么开会话；不支持从一条支线再分支线，也不支持主工作区是裸仓库的布局。
  - 不升级接入项目，那由维护者自己处理。
