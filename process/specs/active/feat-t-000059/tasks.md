# 任务与接力：feat-t-000059

> 门禁状态以 `bash scripts/ai-gate.sh status feat-t-000059` 为准；`.gates` 由脚本维护，禁止手改。

## 1. 方案
- 思路：不加「并行」这个新功能，只把「同一时间只做一个 Spec」这条规矩的范围，从整个仓库改成一个工作区。六轮讨论里试过并放弃的做法（脚本零改动、只靠分支名约定、脚本代建工作区、改 g3 判定）和各自的实测，见任务文件「需求讨论」。实现以原型为底（原型只在临时目录里，不在仓库里），逻辑如下：
  1. **认主工作区**。`ai-config.sh` 加四个小函数。`worktrees` 列出本仓库所有工作区的目录（`git worktree list --porcelain`，第一项是主工作区）。`main_wt` 在别的工作区里输出主工作区的目录，在主工作区或不在 Git 仓库里时没有输出；判据是 `git rev-parse --git-dir` 与 `--git-common-dir` 是否相同，两边都由 Git 给出，不拿路径字符串比较。`branch_wt <分支>` 输出检出了这个分支的工作区目录，目录已经不存在的不算。`own_specs` 列出当前工作区自己的活跃 Spec 目录。
  2. **`own_specs` 的判据**，按顺序：
     - Spec 名等于当前分支名：是自己的（把已经启动的 Spec 挪到同名分支的工作区去做，维护者 2026-11-27 定的）。
     - 本仓库有工作区检出了和 Spec 同名的分支，而且那个工作区里有这个 Spec 目录：已经挪过去了，不是自己的。那个工作区里没有这个目录（主工作区还没提交就开了工作区），或它的目录已经不存在时，这一条不成立。
     - 当前在别的工作区，而它和主工作区的分叉点提交里已经有这个 Spec 目录：是从主线带过来的副本，不是自己的。分叉点取 `git merge-base HEAD <主工作区当前检出的提交>`，后者用 `git -C <主工作区> rev-parse HEAD` 取，不认分支名。
     - 其余都是自己的。只有一个工作区时三条都不成立，结果和现在的 `process/specs/active/*/` 一样。
     - 由第三条带来的一个行为：分支名不同于 Spec 名的工作区合入主线之后，主工作区的提交里有了这个目录，这个 Spec 就归主工作区。归档本来就在主工作区做；归档被拒时，`status` 把它列在哪个工作区，就在哪个工作区接着修（指南里写这一句）。审查建议过「副本一经修改就归修改它的工作区」，没有采用：刚合入时两边的目录相同，判不出来；之后再改，又会两边都认。
  3. **任务池全仓库一份**。`ai-task-pool.sh` 加载 `ai-config.sh`；在别的工作区里把 `POOL` 指到主工作区的 `process/task-pool`，编号扫描的归档和活跃目录也看主工作区的；在主工作区里这些路径和现在一样是相对路径，输出不变。锁、编号、认领因此只有一处。`start-next` 找任务文件用真实路径，写进 requirements.md「需求来源」的固定是仓库内的相对路径。`next` 和 `start-next` 的排队保护改用 `own_specs`。`list` 的「进行中」改成「任何一个工作区里有这个 Spec 目录」。
  4. **`status` 和接手快照**。`ai-gate.sh status` 不带参数时先列 `own_specs`，再对别的每个工作区，在子 shell 里 `cd` 进去列它的 `own_specs`（门的校验要在那个工作区的目录下算指纹），前面加一行写明目录；目录不存在的跳过。`ai-resume.sh owner` 的「活跃 Spec 与断点」改用 `own_specs`；在别的工作区里，开头加一行写明主工作区在哪、任务池和被忽略的本地文件在那里。
  5. **归档只在主工作区做**。`archive` 在别的工作区里直接拒绝并给出主工作区目录。在主工作区里，Spec 目录不在本地而在别的工作区时，提示先把它的分支合进来。归档原有的 g3 复核不动，它在主线的实际状态上判，是合入之后的最后一道检查。
  6. **正式验证的锁**。`ai-verify.sh` 在 Git 仓库里运行时，跑检查前先拿 `<公共 Git 目录>/ai-verify.lock`（路径用 `git rev-parse --path-format=absolute --git-common-dir` 取成绝对路径；用 `noclobber` 写入自己的进程号）。拿不到就等，提示一次，提示里有持锁的进程号和锁文件的位置。锁里记的进程已经不存在时，重读一遍确认还是那个进程号再删锁重拿。退出时删锁。等锁不算验证失败。没人占着时不等待也不输出，所以只有一个工作区时输出不变。审查指出「只在多个工作区时加锁」有空档（主工作区正在验证时新开工作区），改成始终加锁，代码也更少。不设等待上限：上限是个阈值，按约定阈值只放红线配置、由人改，这次不加配置键；等的时候被宿主的命令超时打断，重跑即可，写进指南。清理残留锁仍有一个极小的窗口（两个等待者同时判定同一把残留锁），后果是这一次验证可能相撞，记进活文档。
  7. **`status` 不说假话**。`render_spec` 在三道门都有记录、且 Spec 在 `active/` 下时，再跑一次 g3 的校验；不通过就显示原因，不显示「可归档」。
  8. **指南和入口**。新增 `template/.agents/skills/parallel.md`，以任务文件里实测用的第三稿为底，再改这几处：开工作区写明在主工作区里运行；补一句把已经启动并提交的 Spec 挪出去做时分支起成 Spec 名；任务文件在主工作区的任务池里；等验证锁时被超时打断就重跑；归档被拒后在 `status` 列出它的那个工作区里修；半路放弃一条线时把任务文件的「关联 Spec」改回「无」。`template/AGENTS.md` 改两处指向它，`archive-spec.md` 的归档一步加一句。
- 改动文件：`template/scripts/ai-config.sh`、`template/scripts/ai-task-pool.sh`、`template/scripts/ai-gate.sh`、`template/scripts/ai-resume.sh`、`template/scripts/ai-verify.sh`、`template/scripts/harness-selftest.sh`、`template/.agents/skills/parallel.md`（新增）、`template/AGENTS.md`、`template/.agents/skills/archive-spec.md`、`README.md`、`README.en.md`、`docs/architecture/modules/template-mechanism.md`、`docs/architecture/modules/guidance.md`、`template/.agents/skills/upgrade.md`。`skill/SKILL.md` 只核对；归档时按流程看 `MEMORY.md` 要不要加条目。
- 影响与风险：
  - **行为变化**：凡是 `git worktree` 建出来的工作区，都共用主工作区的任务池，也不能在里面归档。维护者已接受（Q1）。本机三个接入项目只读核对过，没有会被它伤到的用法；其中一个项目在途的同名分支线由判据第一条覆盖（Q2、Q3）。写进升级说明。
  - **体积**：维护者定范围时看到的数字是净增约 41 行。加上 Q3 的判据和这轮审查要补的几处（验证锁的绝对路径、删锁前重读、提示里带进程号；同名分支的工作区要真的有那个目录），原型是净增 54 行。实现时先量行数再往下做，上限按 AC-12 的 60 行；最终数字在 g3 时交给维护者。
  - **加载顺序**：`ai-task-pool.sh` 是 `set -euo pipefail`，新加载的函数在不是 Git 仓库、没有提交、没有共同祖先时都不能让脚本退出；管道里不用会提前关掉输入的 `head`。已有调用关系不变：`ai-resume.sh` 调 `ai-gate.sh status` 和 `ai-task-pool.sh next`，本仓库根目录的 `scripts/` 只转发。
  - **Git Bash**：路径带空格；`kill -0` 探测别的 bash 进程和被强杀的进程（2026-11-27 在本机实测可行）；`git worktree list` 给的是 `D:/…` 形式的路径，只和 Git 自己给的路径比较。
  - **各工作区读自己的配置**：`harness/redlines.conf`、`harness/verify.conf` 都按当前工作区的副本读，和现在一样。
  - **已知而不处理的**（都写进活文档或升级说明）：主工作区有没提交的代码改动时合入，会出现「快进成功、归档被拒」；别的工作区里收录、领取留下的任务池改动在主工作区，等那里提交；用 `git rebase` 同步的那段时间里，主工作区对那条线的显示会暂时不对（指南用 merge）；验证锁只管 `ai-verify.sh`，AI 直接跑检查命令时不受它管；主工作区合入一条分支名不同于 Spec 名的线之后、归档之前，它自己在途的 Spec 和合入的那个并列，`next` 只提第一个（指南写的是按 Spec 名归档）；从别的支线工作区再开工作区时，两个工作区会都认上一条线的 Spec（指南写明在主工作区里开）。
  - **自己用自己**：这个 Spec 就在另一个工作区里做，而本仓库的 `scripts/` 转发到正在改的 `template/scripts/`。脚本改到一半时，不在这个工作区里运行会写任务池的命令；先在临时沙箱里跑通自检。
  - **和 `feat-t-000058` 的先后**：它在主工作区已过验证、等维护者的 g3 决定。本 Spec 合入会让它的验证和审查过期。本 Spec「需人决定：是」，本来就要停在 g3 等维护者，先后届时由维护者定。
- 真的 AI 会话怎么判（AC-10；过 g1 的提交就是定稿，之后不改）。沙箱用本 Spec 最终的 `template/` 生成，是一个 Node 小服务：检查要读不入库的 `.env`，并把服务起在固定端口上跑几秒；每个沙箱用不同的端口。会话是宿主起的 subagent，模型指定 Sonnet 5.5，提示里只给项目目录、维护者的一句原话和「接下来没人在线」；原话把格式和边角都说死，不留要人定的点。判定只看落盘状态、提交记录和会话最后那段报告的原文，不看别的自述。四种情形各跑一次：
  - S1 两个互不知情的会话同时各接一个需求（改的文件不相交）。通过条件：两条任务的编号不同；两个 Spec 都归档在主工作区；主工作区里检查命令通过；主工作区此刻的状态指纹等于最后归档那个 Spec 的 `verification.md` 里的 state；主工作区和别的工作区里都没有残留的活跃 Spec。
  - S2 一个会话同时接两个互不相干的需求，原话要求同时做。通过条件：两个 Spec 都归档在主工作区；其中至少一个是在别的工作区的分支上做完再合进来的（主工作区的 `git reflog` 里有以 `merge` 开头的记录，快进也算）；主工作区里检查命令通过。
  - S3 会话断了之后接手：别的工作区里有一条过了 g1、代码已提交的线，任务池里还排着一条。通过条件：两个 Spec 都归档在主工作区；主工作区里检查命令通过；没有残留的活跃 Spec。
  - S4 主工作区在途的 Spec 已过验证在等人，原话要求新需求别等它。通过条件：新需求的 Spec 归档在主工作区；会话最后的报告里出现主工作区那个 Spec 的名字和「过期」或「重新验证」；主工作区那个在途 Spec 的目录和它的代码文件相对开始时没有改动。
  - 不通过时怎么办：先把落盘状态和原因记下来。原因是原话里还留着要人定的点（那个 Spec 的 requirements.md 有未勾选的问题，或 review.md 的「人工决定」空着）的，把原话补死，只重跑这一个情形，每个情形最多补一次。原因是指南没讲清的，只改 `parallel.md` 的措辞，四个情形整套重跑，最多重跑两轮。脚本有缺陷的，回 Task 1 修，过自检后整套重跑。两轮之后仍有不通过的，如实记为不通过，g3 时交维护者定。
  - 跑之前核对：本节相对过 g1 的那次提交没有改动（`git diff <过 g1 的提交> -- tasks.md` 里没有这一节的行）。
  - 基线不重跑：原样脚本、原样指南下 S4 的结果已记在任务文件（AI 手工绕过排队保护，在同一个工作区建第二个 Spec，先提交代码后过 g1）。S1 到 S3 在原样脚本下没有可比的做法。四种情形都只跑一次，只说明走得通。
- AC-01 对照用的命令串（现在定下，实现时不改）。在一个只有一个工作区的新仓库里依次运行，改前、改后各跑一遍，把输出里的时间戳、状态指纹、行首的提交号和验证耗时换成占位符后比较：
  `intake 需求一` → `next` → `intake 需求二` → `list` → `start-next` → `ai-gate.sh status` → `ai-resume.sh owner` → `archive feat-t-000001`（门没过）→ 填好需求和方案后 `pass feat-t-000001 g1` → 改代码、勾任务后 `ai-resume.sh owner feat-t-000001` → `ai-verify.sh --spec feat-t-000001` → `pass … g2` → 写好审查记录后 `pass … g3` → `ai-gate.sh status` → `ai-gate.sh status feat-t-000001` → `archive feat-t-000001` → 再 `archive feat-t-000001`（已归档）→ `ai-gate.sh status` → `next` → `start-next` → `list` → `ai-resume.sh owner` → `archive feat-t-000002`（门没过）→ `archive nope` → 把 T-000002 的关联改成不存在的 Spec 后 `list` → `ai-new-spec.sh feat-direct` → `next` → `ai-gate.sh status`。共 28 次脚本调用；其中两次 `status` 紧跟在 g3 通过之后，状态没变，不属于 AC-08 改的情形。
- 方案审查结论：第 1 轮（2026-11-27，没参与讨论和起草的 subagent，只读）结论是「改完再过」，五个关键问题都已改进上面的方案和 requirements.md：
  - K1 合入主线后归属会从原工作区转到主工作区：确认是判据的固有结果，写明了行为，AC-03 加了用例；它建议的「副本一经修改就归修改者」没有采用，理由见判据一节。
  - K2 分叉点对着哪个提交没写死、目录不存在的工作区、没提交就开同名分支工作区：三处都按它的建议写进判据和 AC-04、AC-05。
  - K3 验证锁的空档、清理残留锁的竞态、没有出路、路径不统一：改成始终加锁、删锁前重读、提示里给进程号和锁文件位置、用绝对路径；等待上限没有加，理由见第 6 条。
  - K4 AC-01 的边界和断言总数：AC-01 写明对照的命令串不含 AC-08 改的那种情形，总数改成动手前实测。
  - K5 AC-10 有两处不能机械判定、没写不通过怎么办：S2、S4 改成落盘可查的条件，补了不通过时的处理和次数上限。
  - 不阻塞的建议里采用的：`archive-spec.md`、`README.en.md` 列进改动文件，`skill/SKILL.md` 列为核对；`status` 用子 shell 进别的工作区；各工作区读自己的配置写进风险；从支线再开工作区、放弃一条线、归档被拒后去哪修，各在指南里加一句；任务文件在主工作区这件事写进指南。没采用的：`next` 列出全部自己的 Spec（会改单工作区之外的输出格式，指南里按 Spec 名归档已经够用）。
  - 第 2 轮（同一个审查者，只读）：三处没照它建议做的地方，理由它都认；新指出一个关键问题，S4 的第二条通过路径（会话自己标成「需人决定：是」停在 g3 也算过）是空子，已删掉。不阻塞的建议里采用的：对照的命令串现在就定下来；S2 的合入写成 `reflog` 里以 `merge` 开头的记录；跑真会话前核对判据一节没改过；自检加「验证失败时也不留锁」；指南里「放弃一条线」那句补上同名分支的工作区删掉后 Spec 回到主工作区；净增行数的变化提前告诉维护者。结论：改掉 S4 后可以过计划门。

## 3. 发现但不碰
> 范围外的问题只记录：位置 / 现象 / 建议归属。
- `template/scripts/ai-gate.sh` 的 `cmd_pass`：同一道门可以重复 `pass`，`.gates` 里会多出一行同名记录（实测里一个会话同步后重新验证，没有先 `reset` 就又过了一次 g2）。不影响校验结果。建议归属：模板机制，另起任务。
- `template/scripts/ai-task-pool.sh` 的任务池锁：撞锁就挡回、提示稍后重试。四个工作区同一瞬间收录 12 次时 7 次被挡回。真的 AI 会话里还没因此出过问题。建议归属：任务文件里已记触发条件。
- `template/scripts/ai-task-pool.sh` 的 `next`：一个工作区里有不止一个自己的活跃 Spec 时只提第一个。只有一个工作区时不会出现；有多个工作区时只在「合入之后、归档之前」短暂出现。建议归属：模板机制，真出了误导再改。
