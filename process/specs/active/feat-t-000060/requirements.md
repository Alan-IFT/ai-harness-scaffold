## 1. 要做什么
- 做什么：把 feat-t-000059 三轮审查留下、没有当场修的 8 条建议处理掉（清单在 `process/specs/archive/2026-11/feat-t-000059/tasks.md`「发现但不碰」）。
  - 主工作区不是工作区的布局（主工作区是裸仓库、`--separate-git-dir`、项目本身是子模块）：脚本不认多个工作区，各工作区各管各的任务池和归档，和并行功能之前一样。现在这些布局下，别的工作区里收录的任务文件会写进 Git 目录，编号也会撞。
  - 归属判定靠的前提写进并行指南和活文档，连同前提不成立时会怎样、怎么恢复。
  - 写明验证锁只在同一种 bash 里有效，以及拿不到锁时不加锁、照常验证。
  - 其余五条：并行指南里没合入的分支要用 `git branch -D` 删；`elsewhere` 不再在管道里提前退出；任务池目录写不进去时报真实原因；归档后、删工作区前 `status` 还会列出那个 Spec，写进指南；补自检缺的断言。
- 为谁做：用多个工作区并行的接入项目，尤其是主工作区是裸仓库的；以后接手这些脚本的人。
- 不做：
  - 不在裸仓库这类布局里支持并行（共用任务池、跨工作区的状态显示）。只保证不比并行功能之前差。
  - 不给归属加落盘记录，也不让脚本去检查前提：前提写进说明，判错的几种状态记成已知。
  - 验证锁退出时不核对锁里是不是自己的进程号：同一种 bash 里，活着的锁不会被别人换掉；两种 bash 之间锁本来就不成立，核对了也拦不住两边同时跑。
  - 归档后、删工作区前 `status` 的显示不改脚本，只写一句进指南：真实会话里没出现过，接手的人按指南删掉那个工作区就没有了。
  - 不改 `template/.agents/skills/upgrade.md`。升级演练的会话指出过第 1 步有一句没写怎么核对，它自己直接看了任务池、没被难住；这一条不在审查的 8 条里，改它还要重做一次升级演练。
  - feat-t-000059 实现时记下的三条（同一道门可以重复 `pass`、任务池的锁撞了就挡回、`next` 只提第一个 Spec）不在这 8 条里，触发条件各自记着。
