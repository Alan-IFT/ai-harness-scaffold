### 已核对的事实（2026-11-27 实测）
在系统临时目录里把 `template/` 整个复制成一个 Git 仓库，配一条真实的检查命令，用 `git worktree add` 建工作区（下面叫「线」）。除写明「原型」的几条外，全程用原样脚本；原型只改沙箱里的副本，没改任何脚手架文件。沙箱清掉就没有了，结论记在这里。
- **脚本在线里原样可用**：三条线各自走完 g1、g2、g3；`harness-selftest.sh` 在线里 77 项断言全过。线里只有自己的 Spec 时，`ai-resume.sh owner` 和 `ai-task-pool.sh next` 都只认它。
- **快进合入不改变指纹**：线过完三道门后，在主工作区 `git merge --ff-only`，主线的 `ai-state-id.sh` 与线里验证时的值相同；不重新验证，`ai-gate.sh check <feat> g3` 和 `ai-task-pool.sh archive <feat>` 都通过。归档只动 `process/`，指纹仍不变。
- **主线只动 `process/` 时线不受影响**：线过完 g3 后主线新收录一条任务，线 `git rebase main` 后指纹不变，g3 仍有效，直接合入、归档。
- **主线合入了别的线的代码后**：线 `git rebase main` 没有冲突（各线只动自己的 Spec 目录和任务文件），但指纹变了，`check g3` 报「验证已失效」；此时 `ai-gate.sh status` 仍显示「三道门已通过，可归档」（它只看 `.gates` 里有没有记录）。`reset g2` 后重新验证、重新审查才能合入。
- **主工作区领不了第二个任务**：有一个活跃 Spec 时，`intake` 和 `start-next` 都只回「续做活跃 Spec」。
- **线与线互相看不见领取**：线 1 里 `start-next` 领了 T-000001，线 2 里 `next` 仍显示「下一项：T-000001」。
- **任务池的锁和编号不跨工作区**：主工作区建着 `process/task-pool/.lock`，线里 `add` 照样成功；两边各收录一条，都编成 T-000005。
- **分支名所有工作区共用**：同名分支再建一次，Git 报 `a branch named ... already exists`。
- **被忽略的文件不进新工作区**：`PREFERENCES.md`、`.env` 在线里都没有。
- **两条线都往 `MEMORY.md` 末尾加一条**：后合入的那条 `git rebase` 冲突；`.gitattributes` 加一行 `MEMORY.md merge=union` 后自动合并，两条都在。
- **工作区建在主工作区里面**（宿主的默认做法）：不加忽略行时，它出现在主线的 `git status` 和接手快照的未提交清单里，在主线递归搜代码会搜到线里的副本；主线指纹不变（指纹脚本只算文件，这一项是目录）；`git clean -fdx` 的演习显示会跳过它。加忽略行后 `git status` 不再列出。
- **删工作区**：`git worktree remove` 不带 `--force`，里面只有被忽略的文件时直接删掉，有未跟踪或改过的文件时拒绝。
- **「改动指纹」**：把 `git diff --raw --no-renames --full-index <与主线的分叉点> HEAD -- . ':(exclude)process/**'` 的输出取哈希，得到「这条线改过哪些文件、各自改前改后的内容」。别的线改了别的文件、或主线只动 `process/` 时，同步前后不变（rebase 和把主线 merge 进来都一样）；别的线改了同一个文件（隔得远、能自动合并也算）或线里又加了提交时会变；换 `core.autocrlf`、`diff.algorithm` 设置不变。对照组 `git patch-id --stable` 只在改动挨得近（上下文重叠）时才变。合入主线后分叉点就是 HEAD，这份改动算不出来，所以要在快进之前核对。
- **脚本一行不改也能并行，但容易走错**：主工作区照常 `intake`，提交任务文件，`git worktree add -b <Spec 名> <目录>`，再把刚建的 `process/specs/active/<feat>/` 搬进新工作区。四个需求、三条线跑通，全部归档，主线没有合并提交。写这段实验时 AI 自己连错两次：新工作区里还没有 `process/specs/active/` 这层目录，`mv` 把 Spec 文件放错了位置；排着队还没开线的 Spec 目录被 `git add -A` 一起提交进主线，后来开的线里就带着它，主工作区的那份也搬不走。另外主工作区的 `list` 把线里在做的任务显示成「关联异常」，接手快照里看不出有别的工作区。

    - `ai-verify.sh`：仓库有多个工作区时，正式验证同一时间只跑一个，后来的等前一个结束；持锁的进程不在了（比如被宿主超时强杀），锁自动作废。脚本实验：两个工作区同时发起，后发起的等前一个结束后通过，两边都不记失败；同样条件下用原样脚本，后发起的失败并记 1 次连续失败；残留的锁不挡路；只有一个工作区时不加锁。
    - `ai-gate.sh status`：三道门都有记录、但已不对应当前状态时，不再显示「可归档」，改为说明原因（实测：别的线先合入、这条线同步之后）。已归档的 Spec 显示不变。
    - 指南第三稿：同步主线改用 `git merge`（不改写历史，推送过的线不用强推，同步期间 Spec 目录不会消失）；去掉「停下问人谁先合入」，改成照常合入，在报告里说明哪些在途 Spec 的验证因此过期，不替它们重做；「要改同一批文件的」从「不并行」改成「排队通常更省事，人明说不等时才并行」；补了被忽略文件、错开占端口检查各一句。
    - 改完后的数字：五个脚本新增 53 行、删改 12 行，净增 41 行。现有自检 77 项全过；单线程 28 条命令的 182 行输出仍与原样脚本逐字相同；并行场景（改用 merge 同步）54 项、边角场景 14 项、锁和状态显示 16 项断言全过。
    - 共用任务池的压力：四个工作区同一瞬间各收录 3 条，5 条成功、7 条被锁挡回（提示稍后重试），编号不重复，文件完好；三个工作区同一瞬间 `start-next`，1 个领到、2 个被锁挡回，没有重复领取。
  - **第二批 4 个会话**（第六轮原型，指南第三稿，各沙箱端口不同；都是 Sonnet 5.5）：
    - 两个互不知情的会话（一个加 `/health`，一个给文本报告加合计行，文件不相交）：一个就地，一个另开工作区；另开的那条用 merge 同步，同步后重新验证、审查，合入归档。3 次正式验证全部通过。这次两边的验证时间没有重叠，锁没有真的排上队。
    - 一个会话同时接这两个需求：一个自己在主工作区做，另一个另开工作区交给子代理做，两边同时推进。第一个归档；第二个三道门都过了，但主会话发现子代理自己定了一个原话没说的行为（空清单也输出合计行），按「待确认问题」的规则停在合入前等人定。
    - 「甲已过验证在等人，乙别等」：乙在另一个工作区做完，合入归档；报告里主动说明甲的验证因此过期、没有替它重做；甲的 Spec 目录和代码原样未动。
  - 到这里一共 13 个真的 AI 会话（Sonnet 5.5 十二个、Haiku 5.5 一个，模型名都按宿主的运行记录核对过），每种情形只跑了一遍。

没测的：每种情形只跑了一遍真的 AI 会话，说明走得通，不说明稳定；没测 Claude Code 以外的工具（本机 Git Bash 的 PATH 里没有 `codex`、`gemini`）；没在真实的全栈项目上试（沙箱只有一个不入库的配置文件和一个固定端口，没有依赖安装和数据库）；正式验证的锁在真会话里没有真的排上队，只在脚本实验里验证过；接入项目有没有在用多个工作区没查。

### 厂商与托管平台的官方资料（2026-11-27 取页面核对；引文经过抓取工具摘要，公开引用前再对原文）
- Claude Code worktree 文档：默认建在 `.claude/worktrees/<name>/`，分支叫 `worktree-<name>`；`worktree.baseRef` 默认值 `fresh` 是从远端的默认分支分出，设成 `head` 才从本地 HEAD 分出；`.worktreeinclude` 只复制匹配且被忽略的文件；没有讲怎么合回主线。subagent 默认可以再起 subagent（最多三层）；`claude -p` 是官方的非交互模式；代理视图是研究预览，代理团队是实验性功能且不隔离 worktree。
- Codex：CLI 有 `--worktree`（托管的 worktree）和稳定的 `codex exec`；subagent 默认开启；文档提醒多个 agent 同时改代码会冲突。
- Gemini CLI：有官方 worktree 页面，标着实验性，建在 `.gemini/worktrees/`，要手动清理；subagent 文章提醒重度改代码的任务并行会互相覆盖。
- DeepSeek Harness：开源的宿主，开发者预览，没有讲并行流程。
- Anthropic 的 C 编译器文章：任务锁是 `current_tasks/` 下的文本文件，靠 git 同步让后到的换任务；合并冲突由 agent 自己解决；16 个 agent 撞同一个 bug 时并行无益。OpenAI 的 Harness engineering 文章：合并门尽量少，让应用能按 worktree 各起一份。
- GitHub 合并队列：在「目标分支最新版加上排在前面的改动」上跑必需的检查，过了才合，没有提重新批准。GitHub 受保护分支有一个可选项：改动（diff）变了才把已有的批准作废。GitLab 合并列车同理。
- 「一条线过了验证和审查，主线又动了怎么办」：Anthropic、OpenAI、Google 的资料里没有找到说法（没搜穷尽）。

### 第一轮评审的结论（对那份文档）
方向对：一个需求一个工作区、一次合入一个、状态放文件、会话用完就丢、决策批量问。和实测对不上的六处：
1. 「合并后验证还有效」现在就成立（见上），「合入后在主线再验证一次」是多余的，规定主线只许快进即可。
2. 「先同步，再 g2，再 g3」只对第一条合入的线成立，后面每条线的 g2、g3 都要重做。
3. 「只在主线领取」和「第 1 阶段不写新脚本」不能同时成立（主工作区领不了第二个）。
4. 「预计触及范围」已有对应字段（`tasks.md` 的「改动文件」「涉及文件」）；没有脚本读的红线键和活跃 Spec 数量上限是 ADR-0003 删掉的。
5. `MEMORY.md`、模块文档算进指纹、也归审查管，「合入后在主线汇总」等于改了没人验证、没人审的内容。
6. 「隔离交给宿主」反而绑了宿主：各家目录、分支名、分叉起点都不同；`git worktree` 本身是 Git 自带的。
另有三点那份文档没答：线里没有 `PREFERENCES.md`；内存有限怎么办；负责派活和合入的会话断了，新会话怎么知道有几条线。

### 目前的方向（AI 的第六轮提议，未定）
第五轮的主张不变：不加「并行」这个新功能，只把「同一时间只做一个 Spec」这条规矩的范围，从整个仓库改成一个工作区；命令一条不加，人照常说需求。第六轮在它上面补了实测里真出了问题的三处，别的没加。

**脚本管五件事**（都能机械判定）：
1. 任务池全仓库只有一份，放在主工作区。在哪个工作区收录、领取、看清单，结果都一样；编号、认领、锁只有一处。
2. Spec 在哪个工作区启动，就归哪个工作区。排队保护、门禁状态、接手快照只认本工作区自己的；`status` 另外列出别的工作区在途的 Spec 和它们到了哪道门。
3. 归档只在主工作区做。归档按主线当时的状态复核 g3，是合入之后的最后一道检查。
4. 有多个工作区时，正式验证全仓库同一时间只跑一个（第六轮新增，对应需求 7）。
5. `status` 不说假话：三道门的记录过期了，就显示过期和原因，不显示「可归档」（第六轮新增）。

**AI 管流程**，写成一份按需读的指南，`AGENTS.md` 改两处指向它。下面是实测用的第三稿，21 行；正式的措辞在 Spec 里再做新旧对照：

```md
# Skill: 多个需求并行

**使用时机**：已有活跃 Spec 在途，又来了不该等它的独立需求；或接手时 `ai-gate.sh status` 列出了「别的工作区」。
**原则**：一个工作区同一时间只做一个 Spec，并行就是多开工作区。任务池全仓库只有主工作区那一份，在哪个工作区运行任务池命令，读写的都是它；Spec 在哪个工作区启动，就在哪个工作区做。互相依赖的需求照常排队；预计要改同一批文件的，排队通常更省事，人明说不等时才并行。

## Step 1: 开工作区
1. `git worktree add <目录>`，目录放在项目目录外面（如 `<项目目录>-<简称>`）。
2. 进入那个目录，照常 `bash scripts/ai-task-pool.sh intake "原话"`；需求已经排在任务池里的用 `start-next`。
3. 被 Git 忽略的本地文件（`PREFERENCES.md`、`.env` 这类）新工作区里没有：从主工作区读或拷；依赖按项目的安装说明装。
4. 要同时推进，用宿主的办法在那个目录里另开会话（subagent、后台会话、另一个终端都行）；它进目录后照常运行接手命令。

## Step 2: 照常做
三道门、WIP、提交都在这个工作区里，和平时一样。正式验证全仓库同一时间只跑一个，别的工作区在跑时 `ai-verify.sh` 会等；自己直接跑要占端口、数据库的检查时，也先错开。

## Step 3: 合回主线（一次一条）
1. 同步：主工作区先把 `process/` 的改动提交掉，再在这个工作区里 `git merge <主工作区所在的分支>`，有冲突就地解决。
2. 做正式验证和独立审查（放在同步之后，各做一次就够）；g3 通过后提交。
3. 合入并归档：`git -C <主工作区> merge --ff-only <本分支>`，然后在主工作区运行 `bash scripts/ai-task-pool.sh archive <feat>` 并提交。归档按主线此刻的状态复核 g3：对不上（别的线先合入了，或主工作区有没提交的代码改动）就拒绝，回到第 1 步。项目走合并请求的，按项目流程合入，再在主工作区拉取、归档。
4. 删掉用完的工作区和分支：`git worktree remove <目录>`、`git branch -d <分支>`。

合入会让别的在途 Spec 的验证过期，`ai-gate.sh status` 会如实显示；在报告里说明是哪几个，不替它们重做。
```

**人**照常说需求、做决定，不因为并行多出要定的事。谁先合入不问人：先做完的先合入，后合入的那条同步后重新验证、审查；被别人的合入弄过期的在途 Spec，轮到它时再重做。

**七条需求各靠什么**

| 需求 | 靠什么 | 证据 |
| :-- | :-- | :-- |
| 1 人只提需求和做决定 | 命令不变；开工作区、同步、合入、归档由 AI 按指南做；谁先合入不问人 | 真会话里这些步骤都是 AI 自己做的，其中一次由主会话起子代理在另一个工作区里同时做 |
| 2 宿主无关 | 脚本只用 Git 和 bash；指南里和宿主有关的只有一句「用宿主的办法另开会话」 | 分支名任意、游离 HEAD、嵌套目录、带空格的目录都试过；只在 Claude Code 上跑过 |
| 3 简单，默认行为不变 | 只有一个工作区时走原来的路径 | 自检全过；182 行输出逐字相同；没有新命令、配置键、文件、字段 |
| 4 上下文隔离，随时接手 | 一个工作区一个 Spec，WIP 在各自目录；`status` 列出所有工作区 | 会话断了之后的接手试验 |
| 5 共享文件、未跟踪文件 | 冲突在后合入的那条里解决，门禁强制重新验证、审查；被忽略的文件靠接手快照的一行提示和指南的一句话 | 同文件冲突试验；`.env` 各会话都自己从主工作区拷了 |
| 6 参考厂商资料 | 见「厂商与托管平台的官方资料」 | 不适用 |
| 7 内存有限 | 多个工作区时，正式验证同一时间只跑一个 | 脚本实验；真会话里没有出现重叠 |

**代价**
- 五个脚本净增 41 行（原型的数字）。正式做还要加自检用例，改 README 的流程和脚本表、模块活文档、升级说明。
- 一处行为变化：凡是 `git worktree` 建出来的工作区，都共用主工作区的任务池，也不能在里面归档。已经用多个工作区分别维护互不合并的长期分支的项目，升级后那些分支要改用单独的克隆。接入项目有没有这样用，没查。
- 在别的工作区里收录或领取任务，改的是主工作区的任务文件；改动留在主工作区，等那里下一次提交，有时会被就地做事的会话带进它自己的提交。
- 后合入的线，只要主线多了别人的代码，就要重新验证、审查；主工作区在途的 Spec 也一样。这是「审的是当前验证状态」这条现有规则决定的，本方案不改它。
- 主工作区有没提交的代码改动时合入：快进成功、归档被拒，这条线的 Spec 留在主工作区的 active 里，要等主工作区提交后重新验证。只在脚本实验里出现过，真会话里没有。
- 正式验证的锁只管 `ai-verify.sh`；AI 或审查者直接跑检查命令时不受它管，靠指南里那一句。
- 用 `git rebase` 同步的那段时间里，主工作区对这条线的显示会暂时不对；指南已改用 merge。
- 不支持从一条支线再分支线，也不支持主工作区是裸仓库的布局。
- 每种情形只跑了一遍真的 AI 会话；宿主只有 Claude Code；没在真实的全栈项目上试。

**仍然先不做，各记一个触发条件**
- 让 `archive` 代做合入（一条命令合入并归档，合入前先查主工作区干不干净）：真实使用里出现一次上面说的「快进成功、归档被拒」，或 AI 在合入这几步上出错，再做。
- 「改动指纹」（审查跟着改动走，免掉同步后的重审）：重审成了负担再做；它要改 g3 的判定。
- 任务池的锁从「挡回、稍后重试」改成等待：真实使用里收录或领取被挡回造成麻烦再改。
- 工作区数量上限的红线键：出现一次开得太多、人答不过来或机器撑不住再加。
- `MEMORY.md merge=union`：两条线都改它、冲突多到烦人再加。
- 前五轮的提议见本文件的提交历史。

### 验收标准草案（等维护者确认或改）
- 默认行为不变：只有一个工作区时，现有自检全过；一串固定的单线程命令，输出与改前逐字相同。
- 多个工作区（进自检）：
  - 在别的工作区里收录和领取：任务文件进主工作区的任务池，编号不撞，锁是同一把；带着主线 Spec 旧副本的工作区不被它挡住。
  - `list` 各处输出相同，没有「关联异常」；`status` 列出别的工作区在途的 Spec；门的记录过期时 `status` 不显示「可归档」。
  - 在别的工作区里归档被拒；合入后在主工作区归档通过；两条线各自能过检查、合在一起过不了时，后合入的那条归档被拒。
  - 两个工作区同时发起正式验证：后发起的等前一个结束，两边都不记失败；残留的锁不挡路；只有一个工作区时不加锁。
- AI 照着指南做得对（沙箱里真的 AI 会话，先基线后新文字，判定看落盘状态）：至少四种情形，两个互不知情的会话同时做、一个会话同时接两个需求、会话断了之后接手、在途的 Spec 已过验证在等人；模型、次数和判定规则在方案里先写定。
- 体积：脚本净增行数和指南行数的上限在方案里先定；`AGENTS.md` 不超过行数上限；不加命令、配置键、Spec 字段，不约定分支名。
- 说明同步：README、模块活文档、升级说明；行为变化写进升级说明。
