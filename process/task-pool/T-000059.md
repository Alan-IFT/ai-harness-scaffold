### 已核对的事实（2026-11-27 实测）
在系统临时目录里把 `template/` 整个复制成一个 Git 仓库，配一条真实的检查命令，用 `git worktree add` 建工作区（下面叫「线」）。除最后一条写明的原型外，全程用原样脚本，没改任何脚手架文件。沙箱清掉就没有了，结论记在这里。
- **脚本在线里原样可用**：三条线各自走完 g1、g2、g3；`harness-selftest.sh` 在线里 77 项断言全过。线里只有自己的 Spec 时，`ai-resume.sh owner` 和 `ai-task-pool.sh next` 都只认它。
- **快进合入不改变指纹**：线过完三道门后，在主工作区 `git merge --ff-only`，主线的 `ai-state-id.sh` 与线里验证时的值相同；不重新验证，`ai-gate.sh check <feat> g3` 和 `ai-task-pool.sh archive <feat>` 都通过。归档只动 `process/`，指纹仍不变。
- **主线只动 `process/` 时线不受影响**：线过完 g3 后主线新收录一条任务，线 `git rebase main` 后指纹不变，g3 仍有效，直接合入、归档。
- **主线合入了别的线的代码后**：线 `git rebase main` 没有冲突（各线只动自己的 Spec 目录和任务文件），但指纹变了，`check g3` 报「验证已失效」；此时 `ai-gate.sh status` 仍显示「三道门已通过，可归档」（它只看 `.gates` 里有没有记录）。`reset g2` 后重新验证、重新审查才能合入。
- **主工作区领不了第二个任务**：有一个活跃 Spec 时，`intake` 和 `start-next` 都只回「续做活跃 Spec」。
- **线与线互相看不见领取**：线 1 里 `start-next` 领了 T-000001，线 2 里 `next` 仍显示「下一项：T-000001」。
- **任务池的锁和编号不跨工作区**：主工作区建着 `process/task-pool/.lock`，线里 `add` 照样成功；两边各收录一条，都编成 T-000005。
- **分支名所有工作区共用**：同名分支再建一次，Git 报 `a branch named ... already exists`。
- **被忽略的文件不进新工作区**：`PREFERENCES.md`、`.env` 在线里都没有。
- **两条线都往 `MEMORY.md` 末尾加一条**：后合入的那条 `git rebase` 冲突；`.gitattributes` 加一行 `MEMORY.md merge=union` 后自动合并，两条都在。
- **工作区建在主工作区里面**（宿主的默认做法）：不加忽略行时，它出现在主线的 `git status` 和接手快照的未提交清单里，在主线递归搜代码会搜到线里的副本；主线指纹不变（指纹脚本只算文件，这一项是目录）；`git clean -fdx` 的演习显示会跳过它。加忽略行后 `git status` 不再列出。
- **删工作区**：`git worktree remove` 不带 `--force`，里面只有被忽略的文件时直接删掉，有未跟踪或改过的文件时拒绝。
- **「改动指纹」**：把 `git diff --raw --no-renames --full-index <与主线的分叉点> HEAD -- . ':(exclude)process/**'` 的输出取哈希，得到「这条线改过哪些文件、各自改前改后的内容」。别的线改了别的文件、或主线只动 `process/` 时，同步前后不变（rebase 和把主线 merge 进来都一样）；别的线改了同一个文件（隔得远、能自动合并也算）或线里又加了提交时会变；换 `core.autocrlf`、`diff.algorithm` 设置不变。对照组 `git patch-id --stable` 只在改动挨得近（上下文重叠）时才变。合入主线后分叉点就是 HEAD，这份改动算不出来，所以要在快进之前核对。
- **脚本一行不改也能并行，但容易走错**：主工作区照常 `intake`，提交任务文件，`git worktree add -b <Spec 名> <目录>`，再把刚建的 `process/specs/active/<feat>/` 搬进新工作区。四个需求、三条线跑通，全部归档，主线没有合并提交。写这段实验时 AI 自己连错两次：新工作区里还没有 `process/specs/active/` 这层目录，`mv` 把 Spec 文件放错了位置；排着队还没开线的 Spec 目录被 `git add -A` 一起提交进主线，后来开的线里就带着它，主工作区的那份也搬不走。另外主工作区的 `list` 把线里在做的任务显示成「关联异常」，接手快照里看不出有别的工作区。
- **原型：让脚本认得「这个 Spec 在别的工作区里做」**（一次性原型，只改了沙箱副本）：判据是「当前分支自己有同名 Spec 时，别的 Spec 都不算本工作区的；否则看那个 Spec 有没有同名分支」。`ai-config.sh` 加两个小函数，`ai-task-pool.sh` 的 `next` 和 `start-next`、`ai-gate.sh status`、`ai-resume.sh owner` 各用一处，合计净增 14 行，没有删改。现有自检 77 项全过。开线只剩「照常启动、照常提交，再 `git worktree add -b <Spec 名> <目录>`」，不搬目录：四个需求先后开了四条线（同时最多两条），合入顺序和启动顺序不同，全部归档，主线没有合并提交；主工作区的 `list` 显示「进行中」，`status` 标出各线所在的目录，排队的需求不再被线里的 Spec 挡住；线里只认自己的 Spec，别的线合入并删了分支后留下的旧副本也不会被当成在途。
- **脚本一行不改：主线照旧，支线走「不经任务池」的入口**：主线上需求甲照常 `intake`、就地做到一半。从甲开始之前的提交 `git worktree add -b feat-b`，在里面用 `ai-new-spec.sh feat-b` 建 Spec、做完任务。任务池里排着的需求丙，在主工作区把它的「关联 Spec」改成 `feat-t-000002` 并提交，另开工作区同样用 `ai-new-spec.sh` 建 Spec。期间主工作区的 `next`、`status` 只认甲，主线的流程没有变化；`list` 把丙显示成「关联异常」。甲照常归档后，两条支线各自 `git rebase main` → 正式验证 → 审查（各只做一次）→ 主工作区 `git merge --ff-only`，主线指纹与支线验证时相同 → 原样 `archive` 通过，丙的任务文件随 Spec 进了归档目录。主线随后照常 `intake` 下一个需求。主线没有合并提交，脚本没有改动。
- 本仓库本地 `main` 当天领先 `origin/main` 15 个提交。

没测的：没有起真的 AI 会话在线里干活（只用脚本走了流程）；没测 Claude Code 以外的工具（本机 Git Bash 的 PATH 里没有 `codex`、`gemini`）；没在真实的全栈项目上试依赖安装、端口和本地数据库。

### 厂商与托管平台的官方资料（2026-11-27 取页面核对；引文经过抓取工具摘要，公开引用前再对原文）
- Claude Code worktree 文档：默认建在 `.claude/worktrees/<name>/`，分支叫 `worktree-<name>`；`worktree.baseRef` 默认值 `fresh` 是从远端的默认分支分出，设成 `head` 才从本地 HEAD 分出；`.worktreeinclude` 只复制匹配且被忽略的文件；没有讲怎么合回主线。subagent 默认可以再起 subagent（最多三层）；`claude -p` 是官方的非交互模式；代理视图是研究预览，代理团队是实验性功能且不隔离 worktree。
- Codex：CLI 有 `--worktree`（托管的 worktree）和稳定的 `codex exec`；subagent 默认开启；文档提醒多个 agent 同时改代码会冲突。
- Gemini CLI：有官方 worktree 页面，标着实验性，建在 `.gemini/worktrees/`，要手动清理；subagent 文章提醒重度改代码的任务并行会互相覆盖。
- DeepSeek Harness：开源的宿主，开发者预览，没有讲并行流程。
- Anthropic 的 C 编译器文章：任务锁是 `current_tasks/` 下的文本文件，靠 git 同步让后到的换任务；合并冲突由 agent 自己解决；16 个 agent 撞同一个 bug 时并行无益。OpenAI 的 Harness engineering 文章：合并门尽量少，让应用能按 worktree 各起一份。
- GitHub 合并队列：在「目标分支最新版加上排在前面的改动」上跑必需的检查，过了才合，没有提重新批准。GitHub 受保护分支有一个可选项：改动（diff）变了才把已有的批准作废。GitLab 合并列车同理。
- 「一条线过了验证和审查，主线又动了怎么办」：Anthropic、OpenAI、Google 的资料里没有找到说法（没搜穷尽）。

### 第一轮评审的结论（对那份文档）
方向对：一个需求一个工作区、一次合入一个、状态放文件、会话用完就丢、决策批量问。和实测对不上的六处：
1. 「合并后验证还有效」现在就成立（见上），「合入后在主线再验证一次」是多余的，规定主线只许快进即可。
2. 「先同步，再 g2，再 g3」只对第一条合入的线成立，后面每条线的 g2、g3 都要重做。
3. 「只在主线领取」和「第 1 阶段不写新脚本」不能同时成立（主工作区领不了第二个）。
4. 「预计触及范围」已有对应字段（`tasks.md` 的「改动文件」「涉及文件」）；没有脚本读的红线键和活跃 Spec 数量上限是 ADR-0003 删掉的。
5. `MEMORY.md`、模块文档算进指纹、也归审查管，「合入后在主线汇总」等于改了没人验证、没人审的内容。
6. 「隔离交给宿主」反而绑了宿主：各家目录、分支名、分叉起点都不同；`git worktree` 本身是 Git 自带的。
另有三点那份文档没答：线里没有 `PREFERENCES.md`；内存有限怎么办；负责派活和合入的会话断了，新会话怎么知道有几条线。

### 目前的方向（AI 的第四轮提议，未定）
脚本一行不改。主线照旧，支线走现成的入口：
1. **主线照旧**：主工作区就地一个个做，走任务池，和现在完全一样；有支线在做的时候也一样。
2. **不想排队的独立需求开支线**：`git worktree add -b <Spec 名> <目录> <主线上没有在途改动的提交>`（主线空着就是 `main`；主线正在做别的 Spec，就取它开始之前的那个提交），在里面用现成的「不经任务池」入口 `bash scripts/ai-new-spec.sh <Spec 名>` 建 Spec，原话写进 requirements.md，照常走三道门。任务池里已经排着的任务也可以放到支线：先在主工作区把它的「关联 Spec」改成这个 Spec 名并提交，归档时任务文件跟着走。
3. **主线没有在途 Spec 时合入，一次一条**：支线里 `git rebase main`，再做正式验证和独立审查（放在同步之后，就各只做一次）；回主工作区 `git merge --ff-only <Spec 名>`，照常 `archive`，删掉工作区和分支。归档会在主线上复核 g3，状态对不上就拒绝。
- 脚手架要补的只有指南里的几句话。写哪几句不事先定：先在沙箱里让真的 AI 会话按现在的规则做一次并行（基线），看它错在哪，再补对应的句子，然后新旧文字对照。
- 代价：
  - 支线只能在主线空着的时候合入。主线的 Spec 卡住（比如等人决定）期间，做完的支线合不进来；想完全不堵，就让主线空着，需求都放支线。
  - 任务池里的任务放到支线做时，主工作区的 `list` 把它显示成「关联异常」，直到合入归档。
  - 主工作区的接手快照不提支线，要看 `git worktree list`。
  - 主线正在做别的 Spec 时，支线从哪个提交分出要 AI 判断。
  - 支线里没有 `PREFERENCES.md` 这类被忽略的本地文件，要带过去。
- 第三轮的 14 行原型（脚本认得「Spec 在别的工作区里做」）撤回，留作备选。触发条件：真实使用里上面第二、三条造成了误判，或者确实需要任务池里的任务原样用 `intake` 开到支线。
- 仍然先不做、各记一个触发条件的：
  - 「改动指纹」（审查跟着改动走，免掉同步后的重审）：同步后的重审在真实使用里成了负担再做；它要改 g3 的判定。
  - 线数上限的红线键：出现一次线开得太多、人答不过来或机器撑不住再加。
  - `MEMORY.md merge=union`：两条线都改它、冲突多到烦人再加；在那之前同步时在支线里解决。
  - 正式验证的跨工作区排队：出现一次两条线同时跑检查、互相撞端口或数据库再加；在那之前由项目把注意事项记进 `MEMORY.md`。
  - 支线里禁止收录的硬检查：出现一次支线里收录撞了编号再加；在那之前靠指南。
- 前三轮的提议（第二轮：红线键、改动指纹、改 g3、脚本建线；第三轮：约定加 14 行脚本）见本文件的提交历史。

### 验收标准草案（等维护者确认或改）
- 脚本零改动：`template/scripts/`、`template/harness/` 与改前无差异，现有自检全过。
- 主线不受打扰：有支线存在时，主工作区的 `intake`、`next`、`status`、`owner` 对主线 Spec 的输出与没有支线时相同。
- AI 照着指南做得对（沙箱里真的 AI 会话，先跑基线再跑新文字，看落盘状态和运行记录，不看自述）：主线在做一个 Spec 时再说两个互不相干的需求，新文字下它们各在自己的工作区里做完，主线归档后被一条条快进合入并归档；主线每次前进后的 `ai-state-id.sh` 等于那个 Spec `verification.md` 里的 state；主线没有合并提交。次数和判定规则在方案里先写定。
- 撞了也安全：两个改同一个文件的需求，要么没被并行，要么后合入的那条在同步后重新验证、审查才合入；主线上不出现没审过的状态。
- 能接手：新的上下文按指南说得出有几条支线、各在哪个目录、各到哪道门。
- 体积：指南净增的行数在方案里先定上限；`AGENTS.md` 不超过行数上限；不加脚本、红线键、Spec 字段。
