# Skill: 验证与独立审查（运动员与裁判分离）

**使用时机**：tasks.md 的任务全部完成后，过 g2（验证）与 g3（审查）。
**核心原则**：写代码的上下文不审查自己的代码；审查者只看产物、需求和验收标准，不看实现者的自述。

## Step 1: 正式验证（g2）
1. `bash scripts/ai-verify.sh --spec <feat>`：运行 `harness/verify.conf` 的检查命令。
2. 摘要写进 `verification.md`，失败时终端打印输出末尾。验证后代码再变，就重跑。
3. `bash scripts/ai-gate.sh pass <feat> g2`。

## Step 2: 换上下文审查
1. 新开审查上下文（subagent、新会话或另一个 AI 工具），只给 Spec ID 与基准提交。审查者先运行 `bash scripts/ai-resume.sh review <feat> <base-ref>`，按它的输出自己读必读文件与完整 diff。
2. 不提供实现者的解释和“改动很小”之类的前提。
3. 逐项查：
   - **需求**：每条验收标准都有实现和证据；没有超出需求的新行为，每一行改动都能直接对应到需求；验收标准里有「适当」「尽量」这类无法判定的词，按关键问题处理；按实际改动「需人决定」应为「是」（判据见 `new-spec.md`）却写「否」的，也按关键问题处理；实现者改为「是」后不补审方案，由 g3 的人工决定兜底。
   - **正确性**：空值、边界、并发与幂等、错误处理与回滚。
   - **安全**：身份取自登录态、入口有鉴权、查询参数化、无硬编码密钥、入参校验、资源归属校验。
   - **测试**：关键分支有真断言，不是为通过而写。
   - **规则与文档**：对照 `MEMORY.md` 与改动涉及模块的活文档（按 `docs/architecture/00-INDEX.md` 找）：重蹈已记录的坑、或让其中某句不再成立的，按关键问题处理。
   - **指南与记忆**：改了 `AGENTS.md`、指南、模板或 `MEMORY.md` 时，检查有无矛盾和过时内容，有无把一次性经验写成通用结论、混入个人调试信息。
4. 每条结论带 `文件:行` 或命令输出作为证据。只分两档：
   - **关键问题**（必须修）：本次改动引入或加重（新增调用点、扩大影响面也算）的 bug、崩溃、安全漏洞、数据损坏，以及与验收标准不符。
   - **改进建议**（不阻塞）：写进 tasks.md 的「发现但不碰」。
5. 关键问题为 0 就判通过（改善即批准）。有关键问题时实现者只修这些问题，不顺手重构；修完重跑验证、再审一轮；复审只核对上轮关键问题是否解决、修复本身有没有引入新问题。轮次上限是 `harness/redlines.conf` 的 `CR_MAX_ROUNDS`，触顶停下转人工。

## Step 3: 写 `process/specs/active/<feat>/review.md`（g3 按此格式机械校验）

```md
# 审查：<feat>

- 审查者：<独立上下文标识 / 模型 / 会话>
- 未参与实现：是
- CR 轮次：1 / <CR_MAX_ROUNDS>
- 审查状态：<原样复制 verification.md 的 `- state:` 值>
- 审查范围：<base-ref>...HEAD + 工作区（复审写本轮新增的修复提交）

## 结论
- 关键问题：0
- 改进建议：N
- 人工决定：<「需人决定：是」时由 Agent 把风险呈现给人，记录人的原话结论「通过」或「不通过」；Agent 不得代填>
- 决策来源：<对话 / 工单 + 原话摘要>

## 关键问题
（无则写「无」；有则每条：`文件:行` + 现象 + 期望行为）

## 改进建议

## 证据
- 验证：verification.md 的 result / state
```

## Step 4: 审查者的纪律
- 只读：发现问题写报告，不顺手修。不因为“改动小”降级关键问题，也不把偏好写成阻塞项。
- 报告控制在 ~80 行，先结论后证据。

审查通过后：`bash scripts/ai-gate.sh pass <feat> g3`，再按 `archive-spec.md` 归档。
