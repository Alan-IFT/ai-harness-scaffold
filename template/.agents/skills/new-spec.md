# Skill: 需求澄清 → Spec → 方案

**使用时机**：用户提出新需求，或现有 Spec 被 g1（计划）卡住。
**工作模式**：只读侦察 + 写文档；g1 通过前不改业务代码。

## Step 0: 入队与建 Spec
维护者只用自然语言提需求。独立新需求调用 `bash scripts/ai-task-pool.sh intake "原话"`：有活跃 Spec 则只入队，无活跃 Spec 时自动启动并生成 Spec。补充已有需求用 `update <T-ID> "补充"`，已开始的任务同步改 Spec，必要时 `ai-gate.sh reset`。维护者说“先做某项”时用 `prefer <T-ID>`，无活跃 Spec 再 `start-next`。不经任务池的直接需求用 `bash scripts/ai-new-spec.sh <feat>`。

## Step 1: 澄清（先复述，再追问，不替人拍板）
1. 用 3~5 句复述「你要的是 X，因为 Y，做到 Z 就算完成」，让人确认或纠正。
2. 一次只问 1~3 个最关键的问题；含糊处给 2~3 种解释和各自后果，让人选。
3. 定「需人决定」：涉及数据、权限、发布、架构取舍或不可逆操作写「是」，g3 时需要人的当次决定；其余写「否」。

## Step 2: 写 `requirements.md`
- 保留原话；「做什么 / 为谁做 / 不做」各一句，外行能看懂。
- 验收标准每行写通过条件与证据（命令或可观察输出），能写数字就写数字。
- 待确认问题全部回答并勾选后才能过 g1；没有就删掉占位行。

## Step 3: 写 `tasks.md`
- **方案**：思路、改动文件、影响与风险。写新代码前搜一下有没有同类实现可复用；有界搜索调用方与配置，把结论写进「影响与风险」。
- **任务**：1~6 个，每个写涉及文件（反引号路径）和验证方式；单任务超过 5 个文件就拆。
- 「需人决定：是」的需求，编码前让没写过方案的上下文只读审一遍 requirements.md 与 tasks.md（subagent、新会话或另一个 AI 工具都行），结论写回方案。

## Step 4: 过计划门
`bash scripts/ai-gate.sh check <feat> g1`，按报错补齐后 `pass`，再从 Task 1 开始编码。开发中可用 `ai-verify.sh --quick`；收尾按 `code-review.md` 做正式验证与独立审查。
