# Skill: 需求澄清 → Spec → 设计与自审 (Explore, Clarify & Spec)

**使用时机**：用户要规划新功能 / 新需求；或现有 spec 被门禁卡住需要补齐。
**工作模式**：全程只读侦察 + 写文档，**严禁修改业务代码**，也严禁跳过 G1~G3 直接写码。

## Step 0: 极简路由侦察
1. 读 `docs/architecture/00-INDEX.md`，定位相关模块活文档；跨模块任务按需读取多篇。
2. 只读相关模块的公共契约（`index.ts` / `types.ts`），评估影响面与是否已有类似实现。线索不足时做有界仓库搜索。

## Step 1: 访谈式澄清（先复述，再追问，不要替人类拍板）
0. 维护者只用自然语言提出需求，AI 自行处理队列。独立新需求调用 `bash scripts/ai-task-pool.sh intake "原话"`：有活跃 Spec 则只入队并续做，无活跃时自动启动人工指定或最早待办；空池则启动刚收录的需求。明确补充已有需求时调用 `update <T-ID> "补充"`；已开始任务同步修改 Spec 与门禁。维护者说“先做某项”时 AI 调用 `prefer <T-ID>`，无活跃 Spec 则接着 `start-next`。新会话接手或归档后，`next` 只读预览显示有待办时，用 `start-next` 原子选取与启动。收录成功而启动失败时记录输出的 T-ID，查看 `next` 恢复，不要再次 intake。旧 `docs/INTAKE.md` 仅保留历史记录。
1. **复述理解**：用 3~5 句话复述「你要的是 X，因为 Y，做到 Z 就算完成」，让人类确认或纠正。
2. **逐层追问**：先问完成后希望谁采取什么行动、出现什么效果及如何观察，再按 为谁做 → 做什么 → 关键业务规则 → 怎么算完成 → 异常/权限/数据量 的顺序问；
   一次只问 1~3 个最关键的，不要甩 20 个问题的清单。
3. **模糊需求给 2~3 种解释**：列 A/B/C 各自的产品后果与实现代价，让人类选，**不要自己选**。
4. **区分两类问题**：产品问题（需求本身有歧义）必须问清；技术问题（实现约束未知）可先给假设，但写进待确认问题。

## Step 2: 生成 Spec 目录
`intake` 已自动调用 `start-next` 并生成稳定 Spec ID；人工指定后无活跃 Spec 时，AI 也用 `bash scripts/ai-task-pool.sh start-next`。生成的 Spec 包含 `verification.md` 与本地 `reports/`。不在任务池中的既有直接需求仍可用 `bash scripts/ai-new-spec.sh <feature-slug>`。

## Step 3: 写 `requirements.md`
- **§0 四项必答**：做什么 / 为谁做 / 关键业务规则 / 验收标准，一行一句，能被外行判定。
- **原始问题与象限**：保留任务原话，按复杂度和风险定①~④。④只给出分析与人工移交，G1 后不得推进 G2~G7；把结果追加到关联任务文件，若已有 Spec 则移入 archive，不计为交付。①可精简设计；②③要在设计里记人的前置决策。
- **§1 背景、预期结果 + Non-Goals**：写明完成后的行动、效果、基线或观察方式；目标可有挑战性，实现仍遵守简单优先。明确这次不做什么，防止范围蔓延。
- **§2 EARS 需求**：正常流 + 异常边界流（并发、重试、超时、越权、非法输入）。
- **§3 验收标准表**：每行写清「通过条件 / 不通过条件 / 量化证据」，能数字化就数字化（耗时、条数、错误码）；不写「适当」「尽量」这类无法判定的词。空格子过不了 G2，措辞由独立审查把关。
- **§4 待确认问题**：产品 / 技术分开，每条给 A/B/C 选项；全部回答并勾选后才能过 G1。

## Step 4: 写 `design.md`
- **§2 实现顺序**：按依赖图自底向上（存储 → 协议 / 契约 → 逻辑 → 调用方），每步是可运行的垂直切片；
  单步 >5 文件或跨 2 子系统就拆；每 2~3 步插一个检查点。
- **§3 契约与 Schema**：只写签名不写实现；说明旧调用方 / 旧数据的兼容策略。
- **§4 文件清单**：新建 / 修改 / 只读依赖，逐个列真实路径（占位符过不了 G3）。**清单即写权限边界**。
- **状态指纹**：§4 每个精确文件路径单独写成反引号条目，包括测试、验证配置和直接依赖。只有核对 `CUSTOM_CHECK`/测试命令的脚本与配置依赖后，才写「- 指纹范围确认：已核对验证命令及其脚本、配置、测试依赖」来启用 scoped 模式；否则保守全仓。任意 shell 命令的隐含依赖无法自动推断，不能声称清单必然完整。
- **边界前移**：②③在 §2 写「边界样本」并在首次正式 G4 前检查非默认配置、极值、兼容和失败路径；独立 G5 仍照常进行。
- **间接影响**：有界搜索调用方、定时任务、数据管道、配置、权限、报表和相关 Skill；在 §4 写命中与检索依据。无命中也记范围，防止只改显眼的代码。
- **复用检索**：写新代码前搜索同类功能的已有实现，在 §4「复用检索」写搜索范围、命中与复用或不复用理由；已有多种实现时优先收敛，不再新增一种。
- **§5 对抗自审**：默认自己会过度自信，逐条回答「最可能错哪 / 哪个关键前提可从原始材料低成本证伪 / 没处理的边界 / 能否更简单 / 怎么回滚」。
- **独立设计审查（②③默认）**：自审之后、pass g3 之前，换一个没写过方案的上下文只读 requirements.md 与 design.md 审查。任意宿主都可行：支持 subagent 的工具起只读 subagent；否则新开会话或换另一个 AI 工具，只给 Spec ID 与文件路径，不转贴设计者的对话。结论写进 §5「独立设计审查」，问题改入设计；改了需求就先 `reset` 再重过门。
- **§6 待确认问题**：技术假设也写出来，别藏在脑子里。

## Step 5: 写 `tasks.md`
- 3~6 个原子任务，每个给：涉及文件、对应 AC、完成判据、验证命令；任务 >5 文件就先拆。
- 填 **§1 上下文清单**（必读 / 条件读 / 明确不读 / 本次不变量）与 **§4 WIP 初始状态**。
- 在 §1「相关记忆」列出 `MEMORY.md` 中与本任务有关的条目；过期或与代码冲突的先按 `gc-memory.md` 处理。
- 第一个任务标记 `[<<< CURRENT ACTIVE TASK]`。
- ①简单任务可只写一个紧凑任务和单步设计；AC、真实验证、独立 CR 与 G6 证据仍保留。开发中配置 `QUICK_CHECK` 后使用 `ai-verify.sh --quick`，G4 前必须跑正式验证。
- **首次正式 G4 前预检**：逐项对照 requirements.md 的原文锚点与 AC、design.md §4 文件清单、实际代码和项目活文档，确认关键数字、禁止项、时序与失败路径没有被摘要改写；用 `git status --short` 找出未跟踪、未暂存和已暂存的非流程交付物，确认均已纳入审查和提交计划。运行 `git diff --check` 与 `git diff --cached --check`，修复后再做完整验证。可归档前会移动或更新的流程文件不选作正式验证目标。
- 完整验证之后如交付物内容或暂存状态变化，应重跑正式验证并更新摘要；quick 只供开发期反馈，不能代替 G4。

## Step 6: 过机械门并处理未决事项
1. 依次 `bash scripts/ai-gate.sh check <feat> g1`（再 g2、g3），按报错补齐。
2. 通过后 `pass` 到 g3；如产品语义、风险或范围仍有未决选择，写清选项和影响并请人决定。
3. ②③先完成 Step 4 的独立设计审查再 pass g3；①可省略。需求已明确且无待决选择时，从 Task 1 开始。
4. G5 仍须由未参与实现的独立上下文审查。
