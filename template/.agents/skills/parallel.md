# Skill: 多个需求并行

**使用时机**：已有活跃 Spec 在途，又来了不该等它的独立需求；或接手时 `ai-gate.sh status` 列出了「别的工作区」。
**原则**：一个工作区同一时间只做一个 Spec，并行就是多开工作区。任务池全仓库只有主工作区那一份，在哪个工作区运行任务池命令，读写的都是它；Spec 在哪个工作区启动，就在哪个工作区做。互相依赖的需求照常排队；预计要改同一批文件的，排队通常更省事，人明说不等时才并行。

## Step 1: 开工作区
1. 在主工作区里 `git worktree add <目录>`，目录放在项目目录外面（如 `<项目目录>-<简称>`）。
2. 进入那个目录，照常 `bash scripts/ai-task-pool.sh intake "原话"`；需求已经排在任务池里的用 `start-next`。
3. 已经在主工作区启动的 Spec 要挪出去做：先提交，再 `git worktree add -b <Spec 名> <目录>`，分支名必须等于 Spec 名。
4. 被 Git 忽略的本地文件（`PREFERENCES.md`、`.env` 这类）新工作区里没有：从主工作区读或拷；依赖按项目的安装说明装。
5. 要同时推进，用宿主的办法在那个目录里另开会话（subagent、后台会话、另一个终端都行）；它进目录后照常运行接手命令。

## Step 2: 照常做
三道门、WIP、提交都在这个工作区里，和平时一样；任务文件在主工作区的任务池里。正式验证全仓库同一时间只跑一个，别的会话在跑时 `ai-verify.sh` 会等，等的时候被宿主超时打断就重跑；自己直接跑要占端口、数据库的检查时，也先错开。

## Step 3: 合回主线（一次一条）
1. 同步：在这个工作区里 `git merge <主工作区所在的分支>`，有冲突就地解决。
2. 做正式验证和独立审查（放在同步之后，各做一次就够）；g3 通过后提交。
3. 合入并归档：`git -C <主工作区> merge --ff-only <本分支>`，然后在主工作区运行 `bash scripts/ai-task-pool.sh archive <feat>` 并提交，任务池的改动一并提交。项目走合并请求的，按项目流程合入，再在主工作区拉取、归档。
4. 归档按主线此刻的状态复核 g3，对不上就拒绝（别的线先合入了，或主工作区有没提交的代码改动）。这时看 `ai-gate.sh status`：这个 Spec 列在哪个工作区，就在哪个工作区重新验证、审查，再归档。
5. 删掉用完的工作区和分支：`git worktree remove <目录>`、`git branch -d <分支>`。半路放弃的也这样删，再把它的任务文件改回「关联 Spec: 无」；同名分支的工作区删掉后，那个 Spec 回到主工作区。

合入会让别的在途 Spec 的验证过期，`ai-gate.sh status` 会如实显示；在报告里说明是哪几个，不替它们重做。
